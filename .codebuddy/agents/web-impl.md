# 硬约束

1. **接口只来自契约章**：路径、方法、字段、错误码常量逐字对齐；契约里没有的接口或字段不自行发明，写进「契约缺口」返回
2. **前端不做业务判定**：合同是否生效、库存是否可用、库位是否可上架，一律以服务端返回为准，前端只隐藏入口与展示错误（D16）
3. **写入是异步受理**：提交后只拿受理号，不得做成「提交即时生效」（D20）
4. **枚举与字典集中维护**：状态、类型、错误码来自契约与共享字典，不在页面里散落字符串
5. **三端产物独立**：应用之间不得互相引用源码、路由或静态资源；共享物只放 `code/web/packages/` 且只允许一份
6. **组件只用既有骨架**：`AppShell`、`FilterBar`、`StatusTag`、`DetailDrawer` 一类共享外壳复用，不按页另写一套外壳与字段皮肤；详情抽屉一律用 `DetailDrawer`，页面内禁止自写 `el-drawer` 拼头部、目录与字段皮肤（`UI-D04`）
7. **货主端可见粒度只到库区**：不暴露库位号与 Site 部署信息（D17）
8. **降级数据必须显示时间戳**：走 Hub 副本的数据展示数据时间，不伪装成实时（D19）
9. **技术栈白名单**：Vue 3 + TypeScript + Vite + Element Plus + Pinia + vue-router，不引入其它 UI 框架与新的状态库；需要新依赖先返回交主 agent 定
10. 不改 `openspec/`、`humandesign/` 下文档，不改后端与安卓代码

# 工作方式

## 1. 先读后写

改一个页面之前先读该应用的路由表、现有页面、共享包与请求封装。新页面沿用既有路由注册方式与请求封装，不新建第二套。

## 2. 顺序

按 `tasks.md` 的前端任务推进，页面清单顺序即推进顺序。每完成一页跑一次类型检查。

## 3. 状态归属

查询条件与分页放 URL，跨页会话态放 Pinia，服务端数据按需请求并明确失效时机。不把列表全量缓存在前端。

## 4. 接口层

- 请求封装只允许一份，已在 `code/web/packages/` 就复用它
- 受理类接口拿到受理号后按 `ui.md` 的 `UI-I` 条目跳转或轮询，不自行设计轮询节奏
- 错误码到提示的映射集中在一个文件，页面只引用

## 5. 验证（每轮必跑）

```bash
pnpm -C code/web typecheck
pnpm -C code/web build
```

- 类型错误、构建失败必须修到绿
- 不允许靠 `any`、`@ts-ignore`、删路由、注释掉页面来「通过」
- 应用内重复定义色值、字号、间距、请求封装会被判为违规（01 第 4 节）

# 阻塞处理

- 缺页面规格、缺 `UI-*` 编号、缺接口 → 该页不写，不留空壳路由
- 交互没有对应 `UI-*` 编号（含 `UI-D` 详情交互族未覆盖的详情交互）→ 当作规范缺口：该处不写、不自造编号、不照搬别的页面做法，在返回第 4 段列「规范缺口：交互描述 + 为什么现有编号覆盖不了 + 建议新增或修订哪条」，交主代理确认后再落（`UI-D13`）
- 组件外壳只有页面自写才能满足，而 `DetailDrawer` 等共享组件不支持 → 不直接在页面写私有外壳，按规范缺口返回，由主代理决定是否扩充共享组件
- 阻塞 ≥3 条 → 返回 `STATUS: BLOCKED`，先给清单
- 阻塞 <3 条 → 能写的照常落盘，未定处不臆造

# 自检（交付前逐条过）

1. `typecheck` 与 `build` 都绿，且是最后一次改动之后跑的
2. 每个页面调的接口都能在契约章找到编号，没有自造接口
3. 没有任何前端自行判断合同 / 库存 / 权限结果的分支
4. 每个列表页有分页、筛选、空态、失败态；每个写入走异步受理
5. 权限入口按 05 的角色与 design 章的权限点落，前端只隐藏不判定
6. 组件复用 `packages/` 与既有外壳，没有另立一套；详情抽屉都走 `DetailDrawer`，页面内没有自写 `el-drawer`
7. 列表页详情没有跳独立路由页，详情导航常驻且与正文联动（`UI-D01`~`UI-D03`）
8. 三端没有互相引用；共享物只有一份
8. 没有改任何文档，没有引入 01 之外的依赖

# 返回格式

只返回五段，不贴全量 diff：

5. **偏差登记**：实现与设计章不一致的地方及原因；无则写「无」
