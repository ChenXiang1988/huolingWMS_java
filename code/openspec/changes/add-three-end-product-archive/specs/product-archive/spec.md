# Spec Delta

## Purpose

定义商品档案主数据的归属、字段约束、创建编辑查询与停用行为，保证同一货主内编码唯一、数据不物理删除、版本号可追踪，作为三端共用的档案事实来源。

## ADDED Requirements

### Requirement: 档案归属与字段分层

系统 SHALL 为每个商品档案生成全局唯一系统编号，并固定一个归属货主；归属在创建后 MUST 不可变更。字段分为系统生成、货主必填与附属三类，必填字段缺失时 MUST 拒绝提交。

#### Scenario: 三端创建档案带入归属
- **WHEN** 货主端用户在登录上下文内创建档案，或运营端用户为指定货主代建档案
- **THEN** 系统生成系统编号并写入对应归属货主，档案初始状态为草稿

#### Scenario: 必填字段缺失时拒绝提交
- **WHEN** 提交档案时货主系统编码、名称、条码、基本单位或保管条件任一为空
- **THEN** 系统拒绝提交并保持草稿状态，返回可定位到字段的参数错误

### Requirement: 货主内编码判重

系统 MUST 在同一货主范围内保证货主系统编码与条码唯一；不同货主使用相同编码或条码 MUST 互不影响。判重 MUST 在提交审核时执行，草稿态允许重复。

#### Scenario: 同货主重复编码被拒绝
- **WHEN** 货主提交档案，其货主系统编码与该货主名下另一档案相同
- **THEN** 系统拒绝提交并返回业务冲突，原档案与新草稿均保持不变

#### Scenario: 不同货主相同编码放行
- **WHEN** 两个不同货主分别提交相同货主系统编码的档案
- **THEN** 系统分别受理，两个档案均进入待审核

### Requirement: 编辑与版本递增

系统 SHALL 允许草稿态档案由归属货主或有权限的运营修改；启用态档案的字段变更 MUST 通过变更申请或审核流程生效，不得直接覆盖。每次成功变更 MUST 递增版本号。

#### Scenario: 草稿编辑后重新提交
- **WHEN** 货主修改本人草稿并再次提交
- **THEN** 系统记录新版本号并将档案置为待审核

#### Scenario: 启用态字段不得直接改写
- **WHEN** 调用方尝试直接修改已启用档案的必填字段
- **THEN** 系统拒绝并返回状态冲突，原档案内容与版本号不变

### Requirement: 查询与逻辑停用

系统 SHALL 支持按编码、名称、状态、分类与更新时间过滤查询，采用键集分页；“删除” MUST 表达为逻辑停用，数据 MUST 保留，历史单据与库存流水 MUST 可继续按该系统编号追溯。

#### Scenario: 删除转为逻辑停用
- **WHEN** 货主对自有启用态档案执行删除，且该档案未被不可逆流程锁定
- **THEN** 系统将状态改为停用，保留档案与版本号，历史记录仍可按系统编号查询

#### Scenario: 停用后不接新单但存量可走完
- **WHEN** 档案处于停用态，系统收到新接普通入库单或普通出库单
- **THEN** 系统拒绝新单受理；存量单据、仓内作业与货主取回库存仍按该档案继续
