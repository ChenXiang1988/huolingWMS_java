# 库位与库存模型

库位必须有四段物理坐标才能启用；库存以七字段唯一键落台账，库位是唯一锚点、容器是中间层；状态与位置正交，冻结与隔离靠「状态行」表达，不靠新增数量字段。

---

## 问题

**解决**：定住库位的类型与启用条件、库存的唯一键、状态与位置的关系、冻结与隔离怎么落数据、混存容量怎么算、锁定与冻结的区别、三层强制手段。

**不解决**：库存事务流水的表结构（见 11）、分配与选址策略（见 06、17）、仓型差异（见 07）、计费口径（见 08）。

---

## 设计

### 九种库位类型，没有虚拟库位

依据 D26。`loc_type` 只有九种，全部是真实物理位置：

| 类型 | 用途 | 是否参与容量核算 |
|---|---|---|
| STORAGE | 存储位 | 是 |
| RECEIVING | 收货区 | 是 |
| SHIPPING | 发运区、集货位 | 是 |
| DOCK | 月台 | 是（按时段） |
| QC | 质检位 | 是 |
| QUARANTINE | 隔离位 | 是 |
| WIP | 工位即在制位，一个对象两种叫法 | 是 |
| RETURN | 退货位 | 是 |
| SCRAP | 报废位 | 是 |

**没有 VIRTUAL 类型**。待检、隔离、在制、报废都有真实坐标，能被人走到、能被盘点。

**工位不建独立对象**：加工工位、复核台、打包台在模型里一律是 `loc_type=WIP` 的库位，有巷道、货架、层、格四个坐标。这样在制库存能直接参与库存核算、盘点与容量检查，不需要另建一套「在制数量」字段。

代价是工位也要像普通库位一样维护坐标与启用状态；换来的是全仓只有一套位置体系，没有第二套「工位 + 在制量」的影子账。

> 注意与 Open WES 的 WorkStation 区分：它的 WorkStation 是**操作台设备**（绑人、绑格口），库存在容器里，工位不持有库存。本模型把工位当**位置**，库存可以停在工位上，这是两套不同的建模选择。选位置模型是因为 INV-16 要求「在制必须落在真实工位库位」。

### 库位四段坐标非空才能启用

依据 D28。

| 字段 | 含义 |
|---|---|
| 巷道号 | `aisle_no` |
| 货架号 | `rack_no` |
| 层号 | `level_no` |
| 格号 | `bin_no` |

四段全非空 + `verified_at`（最近一次现场指认时间）非空，才允许把状态置为 `ENABLED`。

库位状态只有三种：`ENABLED` / `DISABLED` / `MAINTENANCE`。

**没有「占用 / 空闲」状态**：混存之后占用是渐变量，做成状态字段必然互相覆盖，占用只能实时算。

### 库存唯一键七字段

依据 D29。

```
(owner_id, location_id, container_id, sku_id, batch_no, stock_status, serial_no)
```

| 字段 | 说明 |
|---|---|
| `container_id` | 必须 `NOT NULL DEFAULT ''`。空串表示散货（无容器，直接地堆或上架）；非空表示货在这一个容器里 |
| `serial_no` | 同样 `NOT NULL DEFAULT ''`。联合唯一索引里 NULL 不参与去重，留空会产生重复库存行 |

七个字段全同即同一行库存，不允许出现两行。这条是库存准确性的地基：所有数量增减都作用在唯一确定的一行上。

`container_id` 进唯一键的原因：同一个库位、同一个批次可以分放两托，若不含容器字段只能合成一行，容器号就没地方记。

### 库位是唯一锚点，容器是中间层

依据用户的建模要求与 INV-01。

| 对象 | 能否为空 | 约束 |
|---|---|---|
| 库位 | **不能** | 库存永远有库位，这是 INV-01 的落点 |
| 容器 | 可以 | 空串 = 散货；非空 = 货在该容器内 |

两条一致性规则：

1. **容器有位置时，必须与库存位置一致**：`container.location_id == stock.location_id`，不允许出现「库存记在 A 库位、容器却在 B 库位」。
2. **容器没有位置时，不得有库存挂载**：容器在载具上或空置时 `location_id` 为空，此时不能有库存行指向它，否则库存就失去了库位。

### 容器对象：装载单元，不是位置

| 字段 | 内容 |
|---|---|
| 容器号 | 唯一，可扫码 |
| 容器类型 | 托盘 / 料箱 / 周转箱 |
| 当前所在库位 | `location_id`，**可空**（空表示在载具上或空置） |
| 所属货主 | 可选；托盘一般共用 |
| 状态 | 在用 / 空置 / 停用 |

容器与库位是两件事：**库位是位置，容器是装载单元**。容器可以放在库位上，也可以放在载具上；但库存只在"容器在库位上"时才能挂在容器里。

由此多出一种作业方式：**按容器整体移库**。叉车搬的是托盘不是 SKU，所以移库单可以按容器下，容器内所有 SKU 一次事务一起移，比逐 SKU 行移更贴近现场动作。

### 容量按容器数与散货量分别核算

| 库存形态 | 占容量怎么算 |
|---|---|
| 有容器 | 按容器占格数算（一个容器占一格或半格，由容器规格决定） |
| 散货 | 按件数或体积换算 |

两种形态可以在同一个库位并存，但 `EXCLUSIVE` 库位不允许混。

### 状态与位置正交，两者互不表达

依据 D27。

| 业务语义 | 怎么落数据 | 不动什么 |
|---|---|---|
| 冻结 | 库存从 `AVAILABLE` 行转到同库位的 `FROZEN` 行 | 位置不变 |
| 解冻 | 从 `FROZEN` 行转回 `AVAILABLE` 行 | 位置不变 |
| 隔离 | 库存从存储位转到 `QUARANTINE` 库位 | 状态不变 |
| 移库 | 库存从一个 `STORAGE` 位转到另一个 `STORAGE` 位 | 状态不变 |

「冻结」和「隔离」是两个独立操作，分别留痕。不允许做成一个「库存调整」按钮——那样审计时分不清是状态变了还是位置变了。

### 数量只有两个字段，冻结靠状态行表达

这是本文最关键的一条判断。

| 字段 | 含义 |
|---|---|
| `qty_on_hand` | 在库数量 |
| `qty_allocated` | 已分配未执行数量 |

**不需要 `qty_frozen` 字段**。理由：

1. `stock_status` 在唯一键里（D29），冻结的货天然是**另一行**，不是同一行的另一个字段。
2. 状态与位置正交（D27），冻结只改状态不改位置，所以是「行间转移」而不是「字段增减」。

举例：某库位某批次有 100 件，冻结 20 件：

```
操作前：一行  status=AVAILABLE  qty_on_hand=100  qty_allocated=0
操作后：两行  status=AVAILABLE  qty_on_hand=80   qty_allocated=0
              status=FROZEN     qty_on_hand=20   qty_allocated=0
```

四账户模型里的「冻结量」，在本模型里就是 `stock_status=FROZEN` 的行的 `qty_on_hand` 之和，查询时按状态汇总即可，不占字段。

这条与 13 号文档里 Open WES 的四账户形似而不同：它是同一行四个数量字段，我们是同一键多行。两种都能保证不超卖，我们的好处是唯一键天然约束，坏处是查询要按状态汇总。

### 已分配只对可用库存有意义

依据 INV-08：`qty_allocated <= qty_on_hand`。

| 状态行 | 允许 `qty_allocated > 0` | 理由 |
|---|---|---|
| AVAILABLE | 是 | 只有可用库存能被分配 |
| FROZEN | 否 | 冻结的货不能卖 |
| QUARANTINE | 否 | 隔离的货不能卖 |
| 其他 | 否 | 不可售状态一律不分配 |

上架选址、出库分配都只读 `AVAILABLE` 行。

### 混存容量核算必须含已分配未执行

依据 D30。

```
库位占用 = Σ 在库换算占用 + Σ 已分配未执行换算占用
上架可用 = 物理上限 − 库位占用
```

为什么要把「已分配未执行」算进去：货还没出库，位置还占着，但已经许给别人了。只按在库算，会在同一库位塞进超过上限的货。

上架选址必须在事务内 `SELECT ... FOR UPDATE` 锁库位行，防止两个上架任务同时判定「还剩一格」。

换算占用需要商品侧的换算率：

| 商品 | 换算 |
|---|---|
| 整托商品 | 1 托盘 = 库位 1 格 |
| 整箱商品 | 若干箱 = 1 格，按箱数除 |
| 拆零商品 | 按件数或体积占用 |

换算率挂在商品档案或包装规格上，不写在库位模型里。

### 混存策略三种，独占不得混货主

依据 INV-05。

| 策略 | 允许同一库位放 | 典型场景 |
|---|---|---|
| `EXCLUSIVE` | 只有一个货主，且通常只有一个 SKU | 高值品、危化（首期不做） |
| `SHARED_OWNER` | 同一货主的多个 SKU | 常规存储 |
| `SHARED_ALL` | 任意货主的任意 SKU | 拆零拣选位 |

`EXCLUSIVE` 库位写入第二个货主的库存时，必须在数据库层拒绝，不能只靠应用层判断。

### 库存流水只追加，不可改不可删

依据 INV-09。

| 规则 | 内容 |
|---|---|
| 追加 | 每次数量变化写一条流水，带变动前后值与操作类型 |
| 不可改 | 流水表无 UPDATE 权限 |
| 不可删 | 流水表无 DELETE 权限 |
| 日结 | 每日按流水汇总与库存台账比对，差异即告警 |

流水是库存的唯一审计凭证。台账可以因故障重算，流水不能。

### 日结核对三个数

| 数 | 来源 | 比对对象 |
|---|---|---|
| 台账今日数 | 库存表按七字段汇总 | 昨日台账 + 今日流水净变化 |
| 流水净变化 | 流水表按变动类型汇总 | 台账差额 |
| 单据侧数量 | 已完成的出入库单据汇总 | 台账差额（允许在途差异） |

三者对不上，先查流水断裂，再查跨仓调拨在途（见 10）。

## 强制手段三层

依据 D31，三层缺一不可。

| 层 | 手段 | 例子 |
|---|---|---|
| 数据库 | 约束与索引 | `location_id NOT NULL` + 外键、七字段唯一索引、`loc_type` 取值约束、`qty_allocated <= qty_on_hand` 的 CHECK、四段坐标非空、容器位置一致性校验 |
| 应用 | 只走单一入口 | 库存写入只允许经库存服务、库位启用前校验坐标、上架选址加行锁、货主数据域注入 |
| 核对 | 定时扫描 | 库存与流水日结、库位禁用仍有库存告警、超容扫描、库位码现场指认校验 |

只有数据库约束没有应用校验，会出现「错误但合法」的数据；只有应用校验没有数据库约束，一次脚本就能破坏准确性。三层都要有。

## 约束与验证

| 约束 | 强制手段 |
|---|---|
| 库存必须绑定真实库位 | 数据库层：`location_id` 非空 + 外键；`loc_type` 无 VIRTUAL 取值 |
| 七字段唯一 | 数据库层：联合唯一索引，`container_id` 与 `serial_no` 均默认空串 |
| 容器与库存位置一致 | 应用层：挂载库存到容器前校验；核对层：日结扫描「容器位置 ≠ 库存位置」的行 |
| 无位置容器不得挂库存 | 数据库层：`container_id` 非空时 `location_id` 必非空（组合校验）；核对层：扫描「容器 `location_id` 为空但仍有库存」的记录 |
| 状态与位置正交 | 应用层：冻结与移库是两个独立命令，各自留痕；不允许合并成「库存调整」 |
| 冻结不改位置 | 数据库层：冻结后 `location_id` 与操作前一致（核对脚本）；应用层：冻结命令不接库位参数 |
| 不允许负库存 | 数据库层：`qty_on_hand >= 0` 与 `qty_allocated >= 0` 的 CHECK；应用层：扣减前校验 |
| 分配不超在库 | 数据库层：`qty_allocated <= qty_on_hand` 的 CHECK |
| 不可售状态不得分配 | 应用层：分配查询只取 `AVAILABLE` 行；数据库层：`FROZEN` / `QUARANTINE` 行的 `qty_allocated` 必须为 0 |
| 独占库位不混货主 | 数据库层：唯一键上推不出货主，改用触发器或复合唯一索引（`location_id + owner_id` 对 EXCLUSIVE 库位唯一） |
| 容量不超占 | 应用层：上架前 `SELECT FOR UPDATE` 锁库位行再核算；核对层：超容扫描 |
| 流水不可改 | 数据库层：流水表仅 INSERT 权限 |
| 日结一致 | 核对层：台账、流水、单据三方日结，差异告警 |

引用的决策编号：D26、D27、D28、D29、D30、D31；不变量：INV-01 至 INV-05、INV-08、INV-09；模块归属见 03 M02 与 M03，仓型与层高见 07，任务锁定见 06，调拨在途见 10。

库存事务的表结构与并发实现见 11；分配与选址的具体算法属策略层，不在本文。
