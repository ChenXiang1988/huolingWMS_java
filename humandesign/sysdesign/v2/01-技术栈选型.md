# 技术栈选型

## 1 结论

Java 21 + Spring Boot 3.x 的**模块化单体**，PostgreSQL 16 为主库，Redis 负责分布式锁与热点校验，RabbitMQ 承担跨域异步，移动作业端用 Kotlin 原生开发；全部代码在一个仓库内按部署位置分目录。**不引入 Spring Cloud 全家桶。**

## 3 设计

### 一句话选型表

| 层 | 选型 | 版本基线 | 选它的理由 |
|---|---|---|---|
| 语言 | Java | 21 LTS | 企业生态成熟，虚拟线程可用，长期支持 |
| 框架 | Spring Boot | 3.x 最新稳定 | 单体足够，无需全家桶 |
| 构建 | Maven 多模块 | 3.9+ | 模块边界用 Maven module 强制 |
| 主库 | PostgreSQL | 16+ | JSONB、部分索引、约束能力强 |
| 缓存 / 锁 | Redis + Redisson | 7.x | 任务池、库位锁、扫码校验热数据 |
| 消息 | RabbitMQ | 3.13+ | 事件量级不需要 Kafka |
| ORM | MyBatis-Plus | 3.5+ | 复杂查询需要手控 SQL |
| 库版本管理 | Flyway | 10+ | 表结构变更纳入版本控制 |
| 定时任务 | Spring Scheduling + ShedLock | — | 单机定时 + 多副本防重 |
| 认证 | Spring Security + JWT | — | 三套 token 策略：后台 / 货主 / 移动作业端 |
| 接口文档 | SpringDoc OpenAPI | 2.x | 开放 API 契约的产出源 |
| 可观测 | Micrometer + Prometheus + Loki | — | 指标、日志分离 |
| 运营后台 / 货主门户 | Vue 3 + TypeScript + Vite + Element Plus | — | 中后台生态成熟 |
| 移动作业端 | Kotlin + Android 原生 | minSdk 26 | 一套 App 覆盖工业 PDA 与普通安卓手机；扫码头与摄像头两种扫码通道（D58） |
| 部署 | 全部云上，容器交付；托管 Kubernetes 编排，Site 每仓一套 | — | 镜像统一，靠编排与副本调规模 |

### 仓库只有一个，按部署位置切顶层目录

跨端的共享物多于可分离物：内核、接口契约、状态词表、设计令牌四项必须单一来源，拆成多仓就让这四项退化成手工同步。六个顶层目录各对应一组部署产物，互不打包在一起。

```
huoling-wms/
  backend/        Maven 多模块，一个父 POM
    wms-kernel/     领域内核：库存、库位、任务、不变量（不含 Spring）
    wms-common/     错误码、审计、工具
    wms-hub/        运营管理端      — 可启动
    wms-site/       单仓执行端      — 可启动
    wms-open/       公网接入层      — 可启动
    wms-billing/    计费域          — 可启动，独立库
    wms-archtest/   架构断言：分层与模块边界，只在测试期生效
  web/            前端工作区
    apps/admin/     运营后台
    apps/site/      单仓端（含固定式采集站）
    apps/owner/     货主端
    packages/       三端共享包
  mobile/         Kotlin + Gradle 工程，minSdk 26；一套 App 覆盖 PDA 与安卓手机
  contracts/      接口契约与生成物
  db/             Flyway 迁移脚本
  deploy/         镜像定义、编排清单、云资源定义、反向代理路由
```

`wms-kernel` **不依赖 Spring**，是纯领域模型与不变量实现。四个可启动单元各自打包部署，共享 kernel。

这是模块化单体落地的关键：**不变量只允许在 kernel 里定义**，Hub / Site / Open / Billing 只能调用，不能各写一套校验。

`wms-billing` 单独一个库、单独升级，不与库存库共享（见 00 D49）。它只消费 WMS 推送的作业事实，只回传合同生效状态。

### 前端三端共享代码包，产物按部署位置分开

三端同属中后台形态，共用组件外壳与请求层；但部署位置不同，产物不能合成一个，否则单仓端会被绑上运营后台的发布节奏。

| 端 | 目录 | 部署位置 | 依据 |
|---|---|---|---|
| 运营后台 | `web/apps/admin` | Hub 云上私网区 | 02 三级职责 |
| 单仓端 | `web/apps/site` | Site 云上实例 | D08 部署自治 |
| 货主端 | `web/apps/owner` | Open Platform 公网侧 | 02 货主门户、D18 |

单仓端产物必须能脱离 Hub 与 Open 独立部署：不打包另两端的路由与代码，不引用另两端的静态资源与接口域名。

### 跨端共享物只允许存在一份

| 共享物 | 位置 | 消费者 | 强制手段 |
|---|---|---|---|
| 设计令牌与组件外壳 | `web/packages/design` | 三个前端应用 | 静态检查：应用内不得自定义色值、字号、间距常量 |
| 请求层与错误码映射 | `web/packages/request` | 三个前端应用 | 静态检查：应用内不得直接发起原始请求 |
| 状态词表与术语表 | `web/packages/dict` | 三个前端、移动作业端文案 | 代码评审 + 与 `contracts/` 枚举对账 |
| 接口契约 | `contracts/` | 三个前端、移动作业端、联调测试 | 构建期：生成物与契约不一致即失败 |

依赖方向只有一条：应用依赖共享包，共享包不依赖任何应用，共享包之间不循环，应用之间不互相引用。前端三端与移动作业端之间没有可共享的代码，只共享契约与词表。

### 接口契约由服务端导出，各端只消费生成物

`wms-hub`、`wms-site`、`wms-open` 用 SpringDoc 导出 `openapi.json` 到 `contracts/`，再由生成器产出前端的 TypeScript 类型与移动作业端的 Kotlin 模型。

| 端 | 消费方式 | 不允许 |
|---|---|---|
| 运营后台 / 单仓端 / 货主端 | 生成的类型 + `packages/request` | 手写请求体与响应模型 |
| 移动作业端 | 生成的 Kotlin 模型 | 手写同名字段 |
| 联调与自动化测试 | 契约即桩数据来源 | 按实现反推契约 |

接口变更顺序固定：先改服务端与 `contracts/`，再改各端。反过来做，四端各留一份过期模型。

### 迁移脚本按执行单元分目录

`db/` 下按执行单元分目录，两侧共用的表结构放共享目录，由各单元各自执行同一份脚本。脚本合入主干后不可修改，只能新增。

### 版本与发布按单元独立

| 单元 | 版本号 | 发布触发 | 兼容要求 |
|---|---|---|---|
| 后端四个可启动单元 | Hub / Site / Open 同版本同批；计费域可独立升级 | 改 `backend/` | 三端同步升级，计费域按自身节奏（见 00 D49） |
| 前端三端 | 同一版本，各自产物 | 改 `web/apps/` 分端触发 | 与后端契约版本对齐 |
| 移动作业端 | 独立版本 | 改 `mobile/` | 接口向后兼容至少一版 |

移动作业端必须独立版本：PDA 与手机都在现场，升级分批进行，不可能与后端同批。这条决定了任何破坏性接口变更都要留一个版本的过渡期。

### 部署形态：全部云上，容器交付，Site 每仓一套

仓内不设机房与服务器，现场只有移动作业端（PDA 或手机）与固定式采集站。所有服务单元打成容器镜像，由云上托管 Kubernetes 编排；数据库、缓存、消息队列用托管实例，不进容器。

| 单元 | 云上形态 | 数量 | 区域 |
|---|---|---|---|
| 运营后台 + `wms-hub` | 容器工作负载 | 每法域一套 | 法域内主区域 |
| 单仓端 + `wms-site` | 容器工作负载，每仓独立 | 每仓一套 | 与仓同城或同区域 |
| 货主端 + `wms-open` | 容器工作负载，公网可达 | 每法域一套 | 法域内主区域 |
| PostgreSQL、Redis、RabbitMQ | 托管实例 | 与所属单元同区域 | — |
| 移动作业端 | 不占云资源，走企业分发 | — | — |

前端静态产物打进 Nginx 镜像，与后端单元走同一套发布流程，不依赖云商静态托管特性。

镜像与编排的硬规则：

| 规则 | 强制手段 |
|---|---|
| 一个可启动单元一个镜像 | 构建检查：镜像内只有一个启动入口 |
| 镜像不可变，测试到生产不重新构建 | 发布检查：生产镜像摘要与测试一致 |
| 镜像内不含源码与构建工具 | 构建检查：运行时镜像只拷产物，不带编译链 |
| 应用无状态，不写本地盘 | 部署检查：容器不挂业务数据卷，上传文件落对象存储 |
| 日志到标准输出 | 部署检查：日志采集由编排层负责，容器内不写日志文件 |
| 存活与就绪探针分开 | 部署检查：就绪失败先摘流量，不直接重启 |
| 镜像标签用版本号 | 发布检查：禁止 `latest` |

云资源定义与编排清单放 `deploy/`，与应用代码同仓同版本。仓库内不存环境密钥，密钥由云上密钥服务注入。

### 本地开发：中间件容器化，服务在宿主机跑

本地用一份编排文件起中间件，后端与前端在宿主机跑，改代码即时生效。四个可启动单元默认只起正在改的那个，联调时再全起，省内存也省启动时间。

| 组件 | 本地形态 | 端口 |
|---|---|---|
| PostgreSQL 16 | 容器 | 5432 |
| Redis 7 | 容器 | 6379 |
| RabbitMQ 3.13 | 容器，含管理台 | 5672 / 15672 |
| `wms-hub` | 宿主机，IDE 启动 | 8081 |
| `wms-site` | 宿主机，IDE 启动 | 8082 |
| `wms-open` | 宿主机，IDE 启动 | 8083 |
| `wms-billing` | 宿主机，IDE 启动 | 8084 |
| 运营后台 | 开发服务器 | 5173 |
| 货主端 | 开发服务器 | 5174 |
| 单仓端 | 开发服务器 | 5175 |

本地数据库按单元分三个，各自跑共享与自身迁移，不共用一个库。本地与线上保持一致，跨库问题才在本地就暴露。

种子数据必须包含一份生效合同。`D33` 规定无生效合同不可作业，缺合同的种子数据在本地连收货单都建不出来。

| 规则 | 强制手段 |
|---|---|
| 本地不连云端任何环境 | 提交前扫描：本地配置的连接串只能是 `localhost` 或 `127.0.0.1` |
| 中间件版本与线上一致 | 编排文件锁定镜像标签，与本文件选型表同版本 |
| 种子数据不进生产迁移 | Flyway 分目录：`db/seed/` 不在生产执行路径内 |
| 契约本地可重导 | 一条命令导出 `openapi.json` 到 `contracts/`，流水线校验提交物与最新导出一致 |
| 移动作业端连本地 Site | 模拟器走 `10.0.2.2`，PDA 与手机真机走局域网地址；扫码头扫码与摄像头扫码都要各验一遍 |

`wms-kernel` 的单元测试不依赖 Spring 与容器，直接跑 Maven 测试；只有涉及数据库的集成测试才需要中间件。

### 为什么选 PostgreSQL 而不是 MySQL

| 维度 | PostgreSQL 的优势 |
|---|---|
| 半结构化配置 | 仓型能力矩阵、规则快照、计算参数存 JSONB，可建索引可查询 |
| 唯一约束 | 部分唯一索引处理 `serial_no` 空值，比默认空串更干净 |
| 约束强度 | CHECK、排他约束、延迟约束，能兜住更多不变量 |
| 报表查询 | 窗口函数、CTE 写跨仓聚合更自然 |
| 隔离级别 | RR 下无幻读，减少 MySQL gap lock 的调试成本 |

**可替换性**：如果团队 MySQL 运维更强，换 MySQL 不影响任何设计结论——`location_id NOT NULL`、七字段唯一键、`qty_allocated <= qty_on_hand` 这些约束两种库都能表达。唯一的差异是 `container_id` 与 `serial_no` 用默认空串代替部分索引。

### 为什么 MyBatis-Plus 而不是 JPA

WMS 的查询是典型的多表聚合 + 批量操作，且必须能手工调优执行计划。JPA 的隐式 SQL 在生产环境难定位。

但领域层不直接用 MyBatis：仓储接口定义在 kernel，实现在 infrastructure。**保留替换空间，也防止 SQL 渗透进领域逻辑。**

### 为什么不用 Spring Cloud 全家桶

模块化单体不需要服务发现、配置中心、网关集群、分布式事务框架。真需要的只有三样：

| 需求 | 方案 |
|---|---|
| 限流 | Bucket4j 或 Sentinel 单机版，按货主 + 接口维度 |
| 公网入口 | 云负载均衡，Nginx 只做路由与 TLS 终止 |
| 跨域一致性 | 本地消息表 + 定时补偿，**不用 Seata** |

技术栈通胀是单体项目最常见的死法：先引入 Nacos，再引入 Sentinel，最后为了"规范"拆成微服务，库存就从强一致变成最终一致了。

### 为什么 RabbitMQ 而不是 Kafka

单仓日均单量在万级，事件在十万级，属于任务消息而非流处理。Kafka 的分区规划与运维成本在这个量级不划算。

若后续计费事实流需要回放与批量消费，再单独引入 Kafka，不影响主链路。

## 4 约束与验证

| 约束 | 强制手段 |
|---|---|
| 不变量只能在 kernel 定义 | 代码评审 + ArchUnit 规则校验依赖方向 |
| 四个可启动单元不得互相依赖 | Maven 依赖图检查，kernel 之外只允许单向依赖 |
| 表结构变更只能通过 Flyway | 合入主干的脚本不可修改，只能新增 |
| 中间件版本锁定 | 父 POM 统一管理，禁止模块自行声明版本 |
| 禁止引入 Spring Cloud 组件 | 依赖白名单，新增需改本文件并记入 `log.md` |
| 技术栈变更 | 必须更新本文件 + `log.md` 记录原因 |
| 前端应用之间不得互相引用 | 静态检查：跨应用引用即构建失败 |
| 三端产物必须可独立部署 | 构建检查：单仓端产物不得出现另两端的路由与代码，不得引用另两端的静态资源与接口域名 |
| 跨端共享物只允许一份 | 静态检查：应用内重复定义色值、字号、间距、请求封装即失败 |
| 接口契约变更必须先落 `contracts/` | 流水线顺序：契约生成与校验通过后才允许构建各端 |
| 每仓一套独立资源 | 部署检查：各仓实例与数据库清单独立，跨仓复用同一实例即视为违规 |
| 仓库内不得出现环境密钥 | 提交前扫描：配置文件只允许占位符，实际值由云上密钥服务注入 |
| 有状态组件不进容器 | 架构评审：数据库、缓存、消息队列必须为托管实例，库存真值不落在容器可写层 |
