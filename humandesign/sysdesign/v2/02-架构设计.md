# 架构设计

## 1 结论

系统在云上按「公网接入层 / 运营 Hub / 单仓 Site」三级部署，每仓一套独立 Site 实例，Hub 按法域分区，库存强一致只在单仓内成立；各级只做自己那一段，跨级不共享数据库。

## 3 设计

### 三级各承担一段职责，计费域是独立域（四个可启动单元之一）

| 层 | 面向 | 部署位置 | 负责 | 明确不做 |
|---|---|---|---|---|
| Open Platform | 外部货主 | 云上公网区 | 认证、限流、货主门户、开放接口、回调推送 | 不碰库存、不入库业务判断、不自拼 SQL |
| Hub | 内部员工 | 云上私网区，每法域一套 | 权威主数据（货主、商品、角色权限）、跨仓调度、统一视图 | 不持有库存真值、不做仓内作业、不做出账、不建员工档案 |
| Site | 现场作业员 | 云上私网区，每仓一套 | 库存真值、库位、任务、收发存、加工、设备、本仓员工档案 | 不维护合同与费率、不做跨仓合并出账、不写全局治理角色 |
计费域是第四个可启动单元，不属于上面三级部署层次，单独说明：

| 单元 | 面向 | 部署位置 | 负责 | 明确不做 |
|---|---|---|---|---|
| 计费域 | 计费与对账人员 | 云上私网区，独立库与独立升级 | 合同、费率、算费、账单、对账、财务系统对接 | 不写库存、不做仓内作业、不开票（见 00 D49、D50） |

依据 D06、D49、D50。判断一个功能该放哪层，看它的权威数据在哪：库存与库位、员工档案的权威在单仓端，货主商品与角色权限的权威在运营端，合同、费率与算费的权威在计费域；运营端不持有合同与费率，不做算费与出账。

### Hub 与 Site 之间只走「指令下行、事实上行」

| 方向 | 内容 | 通道 | 失败处理 |
|---|---|---|---|
| 下行 | 主数据变更（含角色与账号）、合同生效状态、调拨单、仓型能力矩阵 | 消息 + 拉取兜底 | Site 保留上一版缓存继续作业，记录待同步标记 |
| 上行 | 库存副本、任务状态、作业事实、设备状态、作业策略配置副本、员工与班组人员副本 | 消息 + 定时对账 | 消息积压不影响作业，Hub 与计费域按事实发生时间补账 |

依据 D12、D13、D59。作业策略参数不在下行之列：它由单仓端维护，运营端只读。

禁止两件事：Site 直连 Hub 数据库；Site 在作业链路上实时反查 Hub 主数据。主数据必须缓存在 Site 本地，作业只读缓存。

### 跨境只传摘要，明细不出境

| 内容 | 是否过境 | 理由 |
|---|---|---|
| 库存总量、单据状态、调拨进度 | 过境 | 跨仓调度与客户查询需要 |
| 库存明细、客户信息、计费明细 | 不过境 | 法域与数据主权 |
| 员工、角色、权限 | 不过境 | 属地管理 |

依据 D07。两个 Hub 之间交换的是摘要，不是副本；摘要字段清单随 02 定稿后由接口契约固定。

### 库存强一致的范围只在单仓内

| 域 | 一致性 | 手段 | 跨仓怎么办 |
|---|---|---|---|
| 库存、库位、分配 | 强一致 | 单库事务 + 行锁 | 跨仓无共享库存，靠调拨两段执行（见 10） |
| 任务状态、指派 | 准实时 | 乐观锁、Redis 原子操作 | 任务不跨仓 |
| 计费、账单 | 最终一致 | 事件驱动、可重算 | 独立计费域合并出账 |
| 报表、看板 | 最终一致 | 异步汇总 | Hub 副本 |

依据 D09、D11、D14。

这张表决定了一件事：**跨仓不存在分布式事务**。调拨的源仓发运与目的仓收货是两个独立本地事务，中间没有在途库存（见 INV 与 D14）。

### 四个可启动单元加一个内核，依赖只允许单向

```
wms-kernel          领域内核（不依赖 Spring）
   ↑      ↑      ↑      ↑
wms-hub  wms-site  wms-open  wms-billing
```

| 单元 | 可依赖 | 不可依赖 |
|---|---|---|
| wms-kernel | 无框架 | 任何可启动单元 |
| wms-hub | kernel | site、open、billing |
| wms-site | kernel | hub、open、billing |
| wms-open | kernel | hub、site、billing |
| wms-billing | kernel | hub、site、open |

依据 D09、D49 与 01 的代码组织。

四个可启动单元之间不互相依赖，跨单元协作全部通过消息或接口契约，不通过共享代码包。否则"模块化单体"会退化成"一个大泥球"。

计费域与 WMS 之间只有两向：WMS 推作业事实（消息），计费域回合同生效状态（下行缓存）。计费域不参与任何库存事务。

### 公网流量与作业流量物理隔离

| 通道 | 优先级 | 资源池 | 限流维度 |
|---|---|---|---|
| 移动作业（PDA 与手机） | 最高 | 独立线程池 | 按仓、按设备，只做保护性限流 |
| 内部管理端 | 高 | 与移动作业端共享应用、独立队列 | 按用户 |
| 外部货主接口 | 低 | Open 独立部署 | 按货主 + 接口 |

依据 D18。外部批量推送打挂仓库是真实事故，隔离的目的是保住移动作业通道。

### 故障边界：Site 挂不影响别仓，Hub 挂不停止作业

| 故障 | 影响 | 降级策略 |
|---|---|---|
| 单个 Site 实例不可用 | 该仓停摆，其他仓与 Hub 正常 | 移动作业端明确提示失败；任务保留在服务端，恢复后继续 |
| 现场到云的链路中断 | 该仓全部作业停摆，移动作业端与采集站都不能用 | 无本地降级（D08 不考虑断网）；链路恢复后继续未完成任务 |
| Site 所在云区域故障 | 该区域内各仓同时停摆 | 无降级手段；异地仓不受影响，恢复依赖云商 |
| 编排控制面故障 | 已运行的容器继续工作，不能新建、不能滚动更新 | 作业不受影响；发布暂停，控制面恢复后继续 |
| 单个工作节点故障 | 该节点上的容器被重新调度，短暂抖动 | 多副本与就绪探针兜住；单副本单元接受秒级中断 |
| Hub 不可用 | 不能改角色与账号、调拨单暂停、统一视图不可用 | 各仓按已缓存的主数据继续作业；员工档案与班组管理不受影响 |
| 计费域不可用 | 不能签合同、不能算费与出账 | 各仓继续作业（合同生效状态已缓存）；作业事实在 Site 侧留存，恢复后补算 |
| Open Platform 不可用 | 货主侧不可用 | 仓内作业不受影响 |
| Redis 不可用 | 任务池、扫码热数据受影响 | 库存事务不受影响（Redis 不存库存真值） |
| MQ 不可用 | 事实与事件积压 | 作业可继续（本地消息表）；计费延后补账 |

依据 D08、D12、D18。降级的前提是"库存真值只在 Site 数据库"，Redis 与 MQ 都不是真值载体。

### 库存真值必须有异地第二份

备份不是可选项。Site 库是库存唯一真值，云区域故障时没有第二份就是丢账，不是停机。

| 对象 | 方式 | RPO | RTO |
|---|---|---|---|
| Site 数据库 | 持续归档 + 每日全量，存另一区域 | ≤ 5 分钟 | ≤ 2 小时 |
| Hub 数据库 | 每日全量 + 增量，存另一区域 | ≤ 1 小时 | ≤ 4 小时 |
| 附件与面单 | 对象存储版本化 + 跨区域复制 | 近实时 | — |
| 密钥与配置 | 云上密钥服务托管，随资源定义重建 | — | — |

| 规则 | 理由 |
|---|---|
| 备份存不同区域 | 同区域备份在区域故障时与生产一起消失 |
| 备份账号与生产账号分离 | 生产账号被误删或被勒索时，不能连带删除备份 |
| 每季度恢复演练一次 | 未演练过的备份视为不可用 |

区域故障恢复的代价要写清楚：从备份拉起后，库存回退到最后归档点，期间未归档的作业记录丢失，必须人工补录并重新盘点确认差异。这是唯一需要人工介入的恢复场景，不能当成自动能力。

备份不替代对账：日结仍是发现不一致的第一道，备份只解决「数据没了」，不解决「数据错了」。

RPO 与 RTO 是目标值，演练验证后再固化，未验证前不得对外承诺。

### 规模只改 Site 的份数与规格，不改拓扑与流程

仓从 5 人到 500 人，变的是 Site 应用副本数、库规格、Redis 是否独立，不变的是三级拓扑、模块边界与单据流程（见 00 D52、D54）。

| 规模带来的变化 | 是否破坏设计 | 前提 |
|---|---|---|
| Site 应用加副本 | 不破坏 | 任务领取与库位锁定不在进程内存，走数据库行锁或 Redis 原子操作 |
| Site 数据库加只读副本 | 不破坏 | 读副本只服务查询，库存写入只走主库 |
| Redis 由共用实例改为独立实例 | 不破坏 | Redis 不存库存真值，可全量重建 |
| 小仓降低资源规格 | 不破坏 | 只减规格不减隔离，仍是一仓一套实例，不与其他仓共用 |

判断标准：规模变化只能动「几份、多大」，不能动「谁是真值、谁写谁读」。任何要靠改拓扑或改流程才能承接规模的方案，都是切错了层。

### 演进按 Site 数量分三阶段，不按时间排

| 阶段 | 形态 | 进入条件 |
|---|---|---|
| 一 | 单 Site + 单 Hub，Open 与 Hub 共用一组云资源 | 首仓上线 |
| 二 | 多 Site，Hub 独立部署，Site 独立升级 | 第二个仓上线，或单仓作业量逼近单实例上限 |
| 三 | 多 Hub 按法域拆分，Hub 间只传摘要 | 出现跨法域仓，或法域合规要求数据不出境 |

阶段推进的判定条件是上面那列，不是时间表。阶段一不预留阶段三的复杂度：不做多 Hub 路由、不做摘要协议、不做跨法域时钟校准。

## 4 约束与验证

| 约束 | 强制手段 |
|---|---|
| 三级不得共享数据库 | 部署检查：Site、Hub 使用独立库与独立账号；连接串不出现在对端配置 |
| 可启动单元单向依赖 | 构建层：Maven 依赖检查；代码层：ArchUnit 规则校验包依赖 |
| 库存强一致不外溢到跨仓 | 设计评审：任何跨仓流程不得要求两端同一事务；10 号文档按两段执行描述 |
| 主数据必须缓存到 Site | 应用层：作业链路的校验只读本地缓存，缺缓存时拒绝作业并告警 |
| 外部流量不得占用移动作业资源池 | 部署层：Open 独立实例；应用层：移动作业端独立线程池与队列 |
| 备份跨区域且账号分离 | 部署检查：备份目标区域与生产区域不同；备份账号与生产账号独立授权 |
| 恢复演练每季度一次 | 运维记录：上一季度无演练记录则冻结重大变更 |
| 降级不得依赖 Redis 与 MQ 存真值 | 核对层：库存日结只比对数据库与流水表；Redis 数据可全量重建 |
| 规模只改规格不改流程 | 设计评审：档位允许的差异项之外一律驳回；上线前按目标并发终端数压测 | 见 00 D52、D54 |
| 加副本不破坏一致性 | 应用层：任务领取与库位锁定用数据库或 Redis 原子操作；压测覆盖多副本场景 | 见 00 D54 |

引用的决策编号：D06、D07、D08、D09、D11、D12、D13、D14、D18、D52、D54、D63、D61、D62；不变量：INV-06、INV-09。

部署拓扑与模块边界的详细分解见 03；库存的账户与锁定语义见 04；并发实现与事务边界见 11。
