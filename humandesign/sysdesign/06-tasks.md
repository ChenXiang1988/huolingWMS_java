# 任务拆分与指派

任务是现场作业的最小执行单元，按三层拆分（作业请求 → 分组 → 执行片），拆片携带已锁定的库存、不重新分配；首期指派到人，状态四态加取消。

---

## 问题

**解决**：定住任务的类型、拆分层次、拆片与库存锁定的关系、指派模式、状态机、与单据的联动方式。

**不解决**：库存账户结构与锁定量字段（见 04）、库位选址（见 04）、设备任务下发（见设备侧）、单据本身的状态机（本文只写任务对单据的回写；单据模型尚未成文，见文末待补项）。

---

## 设计

### 任务按作业类型分五类，拆分维度各不相同

| 类型 | 来源 | 拆分维度 | 拆出来的单位 |
|---|---|---|---|
| 收货任务 | 入库单 | 单据行 + 托盘 | 一托一任务 |
| 上架任务 | 收货完成 | 容器 + 目标库区 | 一容器一任务 |
| 拣货任务 | 出库单 / 波次 | 订单 + 拣货位 | 一单一任务或一批一任务 |
| 移库任务 | 移库单 / 异常处理 | 源库位 → 目标库位 | 一次移动一任务 |
| 盘点任务 | 盘点单 | 库区 / 巷道 / 库位 | 一片区域一任务 |

拆分维度是可配置项，不是硬编码：同一仓型下不同货主可能有不同粒度（整托作业与拆零作业）。配置放在策略层（见 03 M06），任务模块只接收"拆成几个"的结果。

### 出库在单据与任务之间多一层波次

入库一单到底，出库是多单合并作业，所以中间有波次。

本文只保留一条接口约定：**拣货任务组由波次拆出，携带 lock_id**，任务模块不自己决定怎么聚合。

波次本身是产能调度单元，聚合规则、节拍、资源绑定、状态机与库存时机见 [17 波次模型](17-waves.md)。

### 指派策略分三档，随作业量开关

指派方式不是一种，按仓的日均作业量分档，仓级配置，可随时切换：

| 档位 | 适用 | 指派方式 | 策略介入 |
|---|---|---|---|
| 一档 | 日均单量小 | 手动派单，管理者点人 | 无，不计算优先级 |
| 二档 | 日均单量中等 | 按优先级排队，人工确认 | 计算优先级，人工决定派给谁 |
| 三档 | 日均单量大 | 策略派单，系统按负载均衡分配 | 优先级 + 负载 + 作业区就近 |

切换只影响"怎么派"，不改任务模型、不改状态机、不改库存锁定。一档可以完全关掉优先级计算，省掉一部分开销。

**默认一档**。没有配置就是手动派单，不引入任何自动分配逻辑。

### 拆分有三层，职责各不相同

| 层 | 是什么 | 谁创建 | 生命周期 |
|---|---|---|---|
| 作业请求 | 一张单据要做的作业 | 单据模块 | 与单据同寿 |
| 任务组 | 按容器或区域分组后的可指派单元 | 任务模块 | 指派到人后开始，完成后结束 |
| 执行片 | 一次扫码动作对应的最小数量 | 任务组执行时逐步生成 | 秒级 |

举例：一张入库单 200 箱、5 个托盘 → 1 个作业请求 → 5 个任务组（每托一组）→ 每个任务组下有若干个执行片（每箱一片）。

**只有任务组会被指派与人绑定**。执行片不派活，它只是记录"这一扫扫了多少"。

### 拆片必须携带已锁定的库存，不重新分配

INV-10 的落地方式：

```
创建任务组时 → 库存模块锁定 N 个，返回 lock_id
拆执行片时   → 每个片引用同一个 lock_id，声明自己的数量
结案时       → 校验所有片数量之和 = lock_id 的锁定量
```

三条规则：

1. 任务组创建后，锁定量固定；后续拆片只能引用，不能重新向库存申请。
2. 锁定量与任务组是一对一，不允许一个任务组对应多个 lock_id。
3. 结案校验不通过时，任务组不能完成，必须回到"执行中"重新核数。

锁定的具体字段与账户由 04 决定，本文只约定"任务侧持有一个 lock_id 与一个已锁定数量"。

### 指派到人，不是到站

首期两种仓型（楼层仓、平面仓）都是人工仓，没有自动化设备，因此：

| 项 | 首期做法 | 以后 |
|---|---|---|
| 任务归属 | 指派到员工 | 货到人模式下改为指派到工作站 |
| 员工绑定 | 员工码登录后绑定当前设备 | 同一员工可同时绑定多个工作站 |
| 同时任务数 | 一人一个进行中的任务组 | 一人可并行多个站的任务 |

预留方式：任务组上有一个"执行主体"字段，取值为员工或工作站。首期只填员工，不填工作站，也不建设备调度链路。

### 状态四态加取消

```
待指派 → 已指派 → 执行中 → 已完成
  └──────┴────────┴──────→ 已取消
```

| 状态 | 进入条件 | 允许的操作 |
|---|---|---|
| 待指派 | 任务组创建且库存已锁定 | 指派、取消 |
| 已指派 | 绑定员工 | 开始、改派、取消 |
| 执行中 | 员工开始作业 | 记录执行片、报异常、完成 |
| 已完成 | 所有执行片数量之和等于锁定量 | 无（只读） |
| 已取消 | 人工取消或单据取消 | 无，库存锁定量释放 |

四条控制规则：

1. **取消必须释放锁定量**，否则库存会被永久占住。释放由任务模块发起、库存模块执行。
2. **改派只允许在"已指派"状态**，执行中不能换人（换人等于重做）。
3. **完成后不可逆**，出错走冲正单据，不改已完成的任务。
4. **异常不改变任务状态**，只记录异常量；异常处理决定是否拆出补作业任务。

### 任务完成回写单据，不反向调用

任务完成时发领域事件，单据模块订阅后更新自己的状态。任务模块不调用单据模块的接口（见 03 的依赖规则）。

| 事件 | 触发时机 | 订阅方 |
|---|---|---|
| 任务组完成 | 结案校验通过 | 单据模块（推进单据状态） |
| 任务组异常 | 记录异常量 | 单据模块、库存异常记录 |
| 任务组取消 | 取消成功且锁定已释放 | 单据模块 |

### 优先级来自三个来源，不做人工插队

| 来源 | 作用 |
|---|---|
| 单据交期 | 越接近交期优先级越高 |
| 作业类型 | 出库高于入库，越库高于上架 |
| 货主配置 | 货主级的服务优先级（写在合同或服务配置里，见 08） |

不允许操作员手工调整单条任务的优先级：插队一旦允许，现场就会变成"谁喊得响谁先做"。调整只能改单据交期或作业顺序配置。

### 先派单，不做抢单

首期由单仓管理者派单；抢单模式（任务池 + 员工自取）作为以后的能力，需要时只改指派方式，不改任务模型。

## 约束与验证

| 约束 | 强制手段 |
|---|---|
| 拆片不得重新分配库存 | 应用层：拆片接口只接受 `lock_id` 与数量，不暴露"申请库存"入口；核对层：结案时校验分片之和等于锁定量 |
| 取消必须释放锁定 | 应用层：取消与释放写在同一个事务；核对层：日结扫描"已取消但锁定量未释放"的任务组 |
| 改派不改已执行数据 | 应用层：改派前校验状态为已指派；数据库层：执行片记录一旦写入不可改（只追加） |
| 优先级不得人工插队 | 应用层：任务优先级字段只由规则计算写入，不开放修改接口 |
| 指派主体单一 | 数据库层：任务组上"执行主体"字段非空，且员工与工作站互斥 |
| 任务与单据解耦 | 代码层：任务模块不得依赖单据模块的包，ArchUnit 断言 AR-09（见 14） |

引用的决策编号：D24、D25、D51；不变量：INV-10、INV-11；模块归属见 03 M04，库存锁定字段见 04。

任务的时间窗、作业能力、设备下发不在本文范围：时间窗属于作业日历（见 03 M10），设备下发见设备侧文档。
