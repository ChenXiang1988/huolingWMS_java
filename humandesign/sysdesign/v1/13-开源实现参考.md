## 设计

### 库存数量应拆成四个账户，用一个恒等式守住

`00` 目前只有 `qty_on_hand` 与 `qty_allocated` 两个量（见 INV-08）。开源实现给出了更完整的拆分。

| 账户 | 含义 | 来源 |
|---|---|---|
| 总量 | 物理在库 | `SkuBatchStock.totalQty` |
| 可用 | 可被新分配 | `availableQty` |
| 出库锁定量 | 已被出库单占用 | `outboundLockedQty` |
| 非出库锁定量 | 被盘点、加工等其他作业占用 | `noOutboundLockedQty` |
| 冻结量 | 质检、隔离等不可动 | `frozenQty` |

强制手段是一个恒等式，每次变动后校验，任一分量为负或不平衡即抛异常：

```
总量 = 可用 + 出库锁定量 + 非出库锁定量 + 冻结量
```

来源为 Open WES 的 `SkuBatchStock.validateQty()`（见 [04a](../调研/系统/04a-open-wes-功能流程.md) 第 5.3 节）。

对我们的意义：INV-08 只约束了"分配不超在库"，但没有区分"出库占用"与"冻结"。盘点、质检冻结如果复用 `qty_allocated`，出库分配会与冻结互相挤占。

**这一条需要 `00` 决策**：是否把 `qty_allocated` 拆为"出库锁定量 + 其他锁定量 + 冻结量"，或另立 `qty_frozen` 字段。本文不替 `00` 决定。

### 库存写入只能由作业任务触发，不能由单据直接改

开源实现的调用链是固定的：单据 → 任务 → 任务完成 → 库存变动。

| 环节 | Open WES 实现 | 触发点 |
|---|---|---|
| 收货 | 只写收货单与上架任务，不写库存 | `AcceptOrder` 完成后只发事件 |
| 上架 | 上架任务创建时写库存 | `PutAwayAggregate:71` 发 `StockCreateEvent` |
| 拣货 | 作业任务完成时扣减 | `OperationTask:229` 发 `StockTransferEvent` |
| 调整 | 调整单执行时发事件 | `StockAdjustmentAggregate:58` |

反例是若依 WMS：出库单直接调用 `InventoryService.subtract()` 改库存，没有任务层，因此也无法承载"已分配未执行"（见 INV-11）。

对我们的意义：INV-09 要求"库存变动必留事务"，但没有规定事务由谁发起。按任务触发才能同时满足 INV-09 与 INV-11。

### 分配与锁定必须同源，任务拆片携带锁定量

INV-10 要求"任务拆片携带已锁定库存切片，不重新分配"。Open WES 的做法可以照搬结构：

| 动作 | 实现 |
|---|---|
| 分配 | `stockApi.lockSkuBatchStock(dtos)`，每条带 `orderDetailId` 与 `lockQty` |
| 任务生成 | 作业任务持有 `skuBatchStockId` 与 `containerStockId` |
| 扣减 | `subtractAndUnlockQty(qty, lockType)` 同时减总量与锁定量 |
| 重分配 | 先 `lockSkuBatchStocks()` 再生成新任务，避免二次占用 |

来源见 [04a](../调研/系统/04a-open-wes-功能流程.md) 第 3.3、7.2 节。

对我们的意义：锁定量必须记到"单据明细"粒度（`orderDetailId`），不能只记到 SKU 汇总，否则拆片时无法确认哪一片锁了多少。

### 领域事件必须在事务提交后投递，并先落表

01 已定"本地消息表 + 定时补偿"。Open WES 的实现正好是这套：

| 步骤 | 实现 |
|---|---|
| 落表 | 事件先写 `d_domain_event`（事件号、聚合根 ID、类型、JSON 全文） |
| 投递时机 | 有事务时注册 `TransactionSynchronization.afterCommit()`，提交后才发 |
| 投递介质 | 进程内 `EventBus`，跨进程靠接口调用 |

来源见 [04a](../调研/系统/04a-open-wes-功能流程.md) 第 5.4 节。

对我们的意义有两点，其一可借鉴，其一需避开：

1. 可借鉴：先落表再发，事务提交后才投递，与 01 的本地消息表方案同构。
2. 需避开：进程内事件总线在多副本部署时只在当前副本触发。本项目的 Hub 与 Site 都是多副本，事件必须走 RabbitMQ，不能只靠进程内发布。

### 盘点差异不能直接改库存，必须经二次单据入账

Open WES 的链路是两段：

```
盘点记录提交 → 生成库存异常记录（类型为盘点）
            → 另建库存调整单
            → 调整单执行 → 发库存事件 → 库存变动
```

盘点环节一个库存数字都不动，`StocktakeAggregate` 内也没有自动创建调整单的代码。

对我们的意义：INV-09 要求"库存变动必留事务"，若盘点直接改库存，流水里会缺少可追溯的业务动作。两段式让"盘点结果"与"库存调整"各自留痕。

### 任务与设备任务必须分离，用业务任务号关联

D22 只定了设备台账，没定设备任务的建模方式。Open WES 的结构可以直接用：

| 对象 | 作用 | 关键字段 |
|---|---|---|
| 作业任务 | 业务视角的任务 | 工作站、SKU、批次、要求量、实操作量、异常量 |
| 设备任务 | 交给设备执行的动作 | 业务任务号、起点、目标集合、容器编码与面、优先级 |
| 关联表 | 双向查找 | 设备任务与业务任务的关系 |

契约里两个字段最关键（见 [04a](../调研/系统/04a-open-wes-功能流程.md) 第 7.4 节）：

1. `customerTaskId` 存业务任务号，设备回调时靠它找回业务任务。
2. 目标位置是**集合**，支持一次搬运多站停靠。

对我们的意义：INV-10 要求"结案时校验分片之和等于父任务分配量"，只有业务任务与设备任务分离，这个校验才有落点。

### 波次必须有实体，不能挂在明细行上

反例来自 JeeWMS：波次不是对象，只是出库明细行上的三个字段（波次号、状态、首容器），见 [02a](../调研/系统/02a-jeewms-功能流程.md) 第 4.4 节。后果是波次无法独立承载状态、无法统计完成度、无法关联分播格口。

正例来自 Open WES：波次是独立表加独立状态机（新单据 → 处理中 → 完成），拣货单挂在波次下，分播墙格口按工作站与格口编码分配。

对我们的意义：06 任务拆分若涉及波次，必须先定波次实体，否则后续无法按波次核算工时与设备占用。

### 库位选择必须策略化，且限制候选数量

myWMS 给出了唯一一份可读的完整实现（见 [07](../调研/系统/07-mywms.md) 第 7 节）：

| 要素 | 实现 |
|---|---|
| 策略载体 | `StorageStrategy` 一行记录，含区域、是否混放商品、是否混放货主、是否靠近拣货位等开关 |
| 排序 | `sorts` 字段存逗号分隔的排序维度，共九种：货主、库区、区域、容量、分配量、横向坐标、纵向坐标、名称、排序号 |
| 候选上限 | 查库时只取前 30 个候选，再按权重细筛 |
| 入口 | 上架、拣货、同品合并三个独立入口 |

对我们的意义：D10 要求"差异全在策略层"，这套结构是策略层的具体形态。D30 要求上架选址在事务内锁库位行，与"候选上限 30"配合，锁的范围可控。

## 五类反例必须避开

| 反例 | 出处 | 后果 | 本项目对应约束 |
|---|---|---|---|
| 库存读改写不加锁 | 若依 WMS `InventoryService.add/subtract`：先查、Java 里算、整行覆盖写，无乐观锁也无原子更新 | 两单并发时后写覆盖先写，丢更新；"库存不足"校验也拦不住 | D11 强一致、INV-09 |
| 库存由存储过程与视图维护 | JeeWMS：库存视图 `wv_stock` 由存储过程按日刷新，Java 层只有查询 | 库存在单据之外异步变化，无法与单据同事务，口径不可审计 | D09 库存强一致、INV-09 |
| 状态用中文字符串且无单一来源 | JeeWMS：状态常量在三个类里各定义一份，十个状态定义中四个从未被赋值 | 改文案必漏改；状态机无法约束非法流转 | 06 状态机、11 技术落地 |
| 隔离条件手写拼装 | JeeWMS：六十一处手写租户条件，无拦截器 | 漏一处即越权查询 | D02 货主隔离、INV-06 |
| 模块边界名存实亡 | OpenWMS：多个公开子仓库只含启动类，领域实现在闭源依赖包里 | 按仓库名判断能力会误判；无法审计 | D09 模块化单体、01 代码组织 |

另有一条不属反例、但需注意的规模事实：JeeWMS 的业务代码全部集中在一个模块（八百余个类），微服务只是底座外壳。这与 D09 的"模块化单体"方向一致，但它的模块划分没有落地，不能作为模块边界的参考。

## 约束与验证

| 约束 | 强制手段 |
|---|---|
| 四账户拆分若采纳，必须先改 00 | 修订 D11 与 INV-08，记入 `log.md`；未改前 04、11 不得按四账户写 |
| 库存写入只能走单一路径 | 应用层：库存写入仅允许经 `StockService`；核对层：流水与库存日结 |
| 事件必须跨副本 | 架构层：事件投递走 RabbitMQ，禁止只用进程内事件总线；核对层：事件表与投递记录对账 |

| 库位选择限量候选 | 应用层：候选上限写进策略配置；数据库层：`SELECT ... FOR UPDATE` 只锁选中行 |
