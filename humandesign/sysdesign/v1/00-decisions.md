# WMS 系统设计 — 决策记录

> 本文件记录设计讨论中已确定的决策、被否决的替代方案、以及待定项。
> 后续所有详细设计文档必须与本文件一致；如出现冲突，先改本文件，再改设计。

---

## 0. 总纲

系统是一套**单一运营方自用、以货主为唯一隔离维度**的仓储执行系统，部署为「公网接入层 / 运营管理端 Hub / 单仓执行端 Site」三级，形态为模块化单体。

四条不可协商的约束：

1. **位置真实** —— 库存必须绑定有物理坐标的真实库位，不存在虚拟库位；库存状态与物理位置正交表达。
2. **货主隔离** —— 货主是唯一隔离维度，所有货主同构，无内部外部之分，无特权分支。
3. **合同计价** —— 计费入口唯一，合同是唯一价源，无生效合同不可作业。
4. **库存强一致** —— 库存扣减、分配、库位锁定同事务完成，不拆微服务。

其余决策都是这四条在具体场景下的展开，或为支撑它们而存在。

---

## 1. 背景

设计一套仓储管理系统，服务于一家**仓储运营方**，同时承接其自营业务与外部客户的仓储服务。首期仓型只分楼层仓与平面仓，要求支持多人协同作业、任务拆分指派、多维度计费、仓内增值加工，并在数据模型上强制禁止虚拟库位。

---

## 2. 主体与隔离

### D01 无租户概念

系统是单一运营方自用的单套部署，不存在 SaaS 平台级多租户。不建模租户、不做租户开通、不做租户级配置覆盖。

**否决**：`tenant` 作为最外层隔离维度。

### D02 货主是唯一隔离维度

`owner_id` 是系统中唯一的隔离键。所有库存、单据、任务、计费表必含且非空。查询强制注入货主数据域，跨货主访问必须显式授权并留痕。

隔离强度等同于租户级隔离——外部客户之间的库存、任务、账单是商业敏感数据。

### D03 所有货主同构，无内部/外部之分

`owner` 表不设 `type`，不区分内部货主与外部客户，不设任何特权分支。代码中不允许出现 `isInternal` / `ownerType == INTERNAL` 一类的判断。

**否决**：内部货主、内部结算价、内部员工天然可见自营数据的权限特权、自营仓默认开通。

### D04 自营业务建为普通货主

自营业务在系统中就是一条普通货主记录，走完全相同的单据、库存、任务、计费链路。

### D05 所有货主一律计费，差异只在合同

计费入口唯一：`货主 → 合同 → 费率卡 → 计费规则 → 事实 → 明细 → 账单`。没有第二条价源路径。

"自营 vs 服务"的口径差异属于报表层，不进核心模型、不影响任何业务分支。

### D40 货主开通即获全仓网访问权，不做仓级授权

货主账号开通后即可访问仓网内全部仓库的数据，不逐仓授权，不维护「货主—仓库」白名单，不设仓级可见性开关。

访问权与作业准入是两件事：

| 概念 | 决定什么 | 判定依据 |
|---|---|---|
| 访问权 | 能查、能提交 | 货主账号有效 |
| 作业准入 | 能不能实际收货、上架、发货 | 该货主有生效合同（见 D33） |

合同挂在货主上、覆盖全仓网（见 D32），但它是计费与作业门槛，不是访问授权。

**否决**：货主—仓库白名单、按仓开通、仓级数据可见性开关。

这条与 D17 一致：货主只面对一个入口，不感知仓库部署位置与数量。

### D41 仓库建完不等于生效，部署绑定且仓内可作业才生效

仓库有五个状态，状态由 Hub 权威，「已部署」这一事实由 Site 上报：

| 状态 | 进入条件 | 允许做什么 | 禁止做什么 |
|---|---|---|---|
| 拟定 | 仓网建仓 | 签合同、配费率、定仓型与库区规划、下发档案 | 接单、持有库存 |
| 已部署 | 单仓端部署完成，按仓库编码绑定并通过三项校验 | 建库位、配作业日历、期初盘点 | 接业务单 |
| 生效 | 已部署 + 至少一个启用库位 + 作业日历已配置 | 全部作业 | — |
| 停用 | 人工停用 | 存量盘点、移库、出库清仓、已受理单继续完成 | 受理新单 |
| 归档 | 库存为零且人工归档 | 只读查询 | 任何库存变动 |

三项绑定校验：仓库编码存在、状态不是停用或归档、法域与部署配置一致。任一不过，单仓端拒绝启动。

三条硬规则：

1. 单仓端不自建仓库，也不改仓库档案，只读下行副本。
2. 生效不能只看部署：没有启用库位就没有收货落点，没有作业日历就不知道什么时候能作业。
3. 库存不为零不得归档（与 INV-18 同源）。

状态流转只有下面六条，不在这张表里的流转一律拒绝：

| 从 | 到 | 触发者 | 前置条件 | 不满足时 |
|---|---|---|---|---|
| （无） | 拟定 | 仓网管理员 | 编码全仓网唯一、仓型有效、法域填写 | 拒绝创建 |
| 拟定 | 已部署 | 单仓端自动上报 | 三项绑定校验通过 | 启动失败，状态不变 |
| 已部署 | 生效 | 单仓管理者手动启用 | 至少一个启用库位、作业日历已配置 | 保持已部署，列出缺项 |
| 已部署、生效 | 停用 | 仓网管理员 | 无 | — |
| 停用 | 生效 | 单仓管理者手动启用 | 重新校验"已部署"与"生效"的全部条件 | 保持停用，列出缺项 |
| 停用 | 归档 | 仓网管理员 | 库存为零、无未完结单据 | 拒绝，提示未清数量 |

四条控制规则：

1. **不允许回退**：已部署不能退回拟定；仓库一旦下发过，就不能当作没建过。
2. **生效必须人工触发**，不由系统自动判断。现场要确认库位真的可用了，不能由后台替现场下结论。
3. **每次状态变更必须留痕**：操作人、时间、原状态、新状态、原因、缺项快照（生效失败时）。
4. **仓库不物理删除**，只能归档（与 INV-18 同源）。

权限：建仓、停用、归档由仓网管理员；启用由单仓管理者；单仓端只上报「已部署」事实，无权改其他状态。

**否决**：建仓即生效、单仓端本地建仓、绑定失败仍允许启动、系统自动启用、仓库物理删除。

### D42 仓型只分楼层仓与平面仓，建筑参数单列

仓型只有两个值：`楼层仓`、`平面仓`。首期不加第三类。

仓库档案必须记录三项建筑参数：

| 字段 | 含义 | 用途 |
|---|---|---|
| 层高 | 地面到梁底净高 | 货架可建高度与库位高度上限的依据 |
| 建筑面积 | 建筑轮廓面积 | 仓容规划、面积类口径 |
| 可用面积 | 扣除柱网、通道、办公、消防后的可作业面积 | 仓容规划与利用率 |

三条规则：

1. 层高与建筑面积必填；可用面积不得大于建筑面积。
2. 层高是库位高度的上限，库位高度不得超过所在仓的层高（约束落地见 04）。
3. 可用面积是静态规划值，不是实时计算值；变更必须留痕。

仓库属性分四层，四层是四件不同的事，不得合并：

| 层 | 归属 | 判定依据 | 例子 |
|---|---|---|---|
| 建筑形态 | 仓库本体 | 建筑结构 | 楼层仓、平面仓、层高、建筑面积、可用面积 |
| 温区设施 | **库区**，不是仓库单值 | 仓内是否建了这一片温区（保温结构 + 制冷设备） | 常温区、冷藏区、冷冻区 |
| 许可与资质 | 仓库主体持有的证照 | 有没有这个许可，与空间无关 | 危化品经营资质、消防验收 |
| 监管区域 | 仓库所处位置所属的区域 | 仓库落在哪片监管区内 | 保税区、监管作业场所 |

两条关键区分：

1. **温区是物理设施，不是资质**：一个仓可以同时有常温区和冷冻区，所以温区挂在库区上，仓库层面只做汇总（本仓有哪些温区）。一个仓只有一个温区时，也是逐个库区标。
2. **资质是许可，不是物理属性**：仓库没有危化资质，只说明不能存危化品，不说明它的建筑或温区有什么不同。

**不做**：把温区写成仓库单值、把资质写成空间属性、把保税状态写进仓库档案。

**否决**：仓型枚举混入温区或资质、用建筑参数表达监管状态、一个仓多个层高（首期按仓库整体记一个值）。

### D43 仓库层级只到仓与库区，不建楼层对象

首期不建模"楼层"作为独立对象：一个仓一个层高、一个面积。楼层仓的多层差异通过库区划分表达。

若后续出现同一仓内层高差超过 30% 的情况，再评估是否引入楼层对象；在此之前不加表、不加字段。

**否决**：首期引入楼层实体、按楼层拆面积。

### D44 首期只做轻加工，不做多级物料清单

| 类型 | 投入 → 产出 | 是否需要组成关系 |
|---|---|---|
| 贴标 | 同 SKU → 同 SKU，只加标签 | 否 |
| 换包装 | 同 SKU → 同 SKU，改包装规格 | 否 |
| 组合 | 多个 SKU → 一个套装 SKU | 需要单层组成关系 |
| 拆包 | 一个套装 SKU → 多个 SKU | 同上，反向 |

四条规则：

1. 组合与拆包用**单层组成关系**表达（套装 = 若干子件），不做多层嵌套、不做配方比例。
2. 加工单只记三组数量：投入、产出、损耗。损耗必须有去向（报废、返工、差异）。
3. 在制必须落在真实工位库位（见 INV-16），工位库位是 `loc_type=WIP`。
4. 投入减产出减损耗必须为零，差异走冲正，不允许挂账（见 INV-17）。

**不做**：多级物料清单、配方、工序级领料、报工——这些属 MES 范围。

**否决**：把加工做成简化版 MES。

### D45 货主可见的库位粒度由仓库配置，默认只到库区

| 配置值 | 货主端能看到 |
|---|---|
| 库区（默认） | 库区名称与该库区的汇总数量 |
| 库位 | 库位编码与每个库位的数量 |

四条规则：

1. 配置挂在仓库上（见 M10），一个仓一个值，不按货主单独配。
2. 只影响展示，不影响库存记账与作业。
3. 变更必须留痕并写明原因。
4. 无论哪种粒度，都不得暴露其他货主的库存（见 D02）。

**否决**：按货主单独配置可见粒度、按单据临时放开可见范围。

### D46 温区首期建模，字段挂在库区上

| 项 | 内容 |
|---|---|
| 字段位置 | 库区（不是仓库、不是库位） |
| 取值 | 常温、冷藏、冷冻 |
| 首期填值 | 所有库区统一填常温 |
| 仓库层 | 不存温区单值，只汇总本仓已配置的温区种类，供筛选与展示 |

规则：

1. 字段现在建，不省略；冷库仓上线时改库区配置即可，不改表。
2. 首期不做商品温区与库区温区的匹配校验（只有常温，没有可匹配的差异）。
3. 未来启用温区匹配时，在 04 增加"商品温区要求 + 上架同温区校验"，不改本决策的表结构结论。

**否决**：温区存成仓库单值、温区存成库位级字段。

### D47 保税状态首期建模，记在仓库上

| 项 | 内容 |
|---|---|
| 字段 | 仓库档案的 `regulatory_zone` |
| 取值 | 普通、保税 |
| 首期填值 | 所有仓填普通 |

规则：

1. 该字段只表达"这个仓落在哪类监管区域"，不代表仓库的物理属性。
2. 不带账册、不带申报、不带关务流程——关务归下层服务，WMS 只消费结果摘要。
3. 保税货与普通货的混放卡控规则在 04 定义，本决策只定字段位置。

**否决**：把保税做成仓型、把保税做成建筑参数、在 WMS 内做保税账册。

### D48 首期只做普通货，不建危化资质字段

危化品经营资质属于仓库主体的许可，与建筑形态、温区设施都无关。首期不纳入：

1. 不建资质字段，不做资质校验，不建危化专区。
2. 未来纳入时，作为仓库主体的一条许可记录（证号、有效期、许可范围），仍不写进仓库档案的物理属性。

**否决**：用资质字段表达空间能力、用仓型表达资质。

### D49 计费独立成域，是第五个可启动单元

计费不属于 Hub，也不是内核里的一个模块：

| 项 | 内容 |
|---|---|
| 代码 | 独立模块、独立启动单元 |
| 数据 | 独立 schema，不与库存、任务同库 |
| 输入 | WMS 推送的作业事实：收发存、加工、存储天数、资源占用 |
| 职责 | 合同、费率卡、规则、算费、计费明细、账单、对账 |
| 不做 | 不写库存、不改任务、不做仓内作业 |

两个方向的交互：

| 方向 | 内容 | 方式 |
|---|---|---|
| WMS → 计费 | 作业事实 | 异步消息，至少一次，按事实号幂等去重 |
| 计费 → WMS | 合同生效状态 | 下行缓存到 Site，供作业受理校验（见 D33） |

这条不违反 D09：D09 要求强一致的只有库存、库位、分配；计费本来就是最终一致。

**否决**：把计费算在 Hub 进程里、让计费读写库存表。

### D50 计费域到对账为止，开票与总账归财务系统

| 环节 | 归属 |
|---|---|
| 合同、费率卡、计费规则 | 计费域 |
| 事实归集 | 计费域（WMS 推送） |
| 算费、计费明细、账单 | 计费域 |
| 与货主对账、内部对账 | 计费域 |
| 应收、开票、总账 | 财务系统（如金蝶） |

对接方式：计费域向财务系统推送账单或应收凭证，接收回执；差异走对账流程处理，不在 WMS 内改账，也不在计费明细上直接改数（见 D36）。

**否决**：在 WMS 内开发票、把总账做进计费域、账单与财务系统双写。

### D51 采用领域模型，但不采用事件溯源与读写分离

采用的四个模式：

| 模式 | 在本项目的落地 |
|---|---|
| 限界上下文 | 仓储作业域、仓网运营域、计费域、接入域 |
| 聚合 | 库存、任务、单据等聚合根，一致性边界由聚合根划定 |
| 值对象 | 数量与单位、库位编码、批次号、库位四段坐标 |
| 领域事件 | 跨聚合通知，事务提交后投递 |

不采用的两个：

| 不用 | 理由 |
|---|---|
| 事件溯源 | 库存要随时查实时量，重放成本高；流水表只做审计，不作为状态来源 |
| 读写分离（CQRS） | 首期单仓万级单量不需要；读写分离带来的延迟与库存强一致相冲突 |

三条硬规则，全部机器检查：

1. 聚合根不暴露 setter，状态只能由聚合根自己的方法修改。
2. 改状态、校验不变量、发事件都在聚合根内完成；Service 只做"取出、调用、保存"。
3. 上述规则与依赖规则由 ArchUnit 在构建期断言，失败即阻断合并，**不靠人工代码评审**。

**否决**：贫血模型加大 Service、事件溯源、CQRS、靠人工评审保证模型质量。

### D52 规模按作业量分三档，只影响规格与策略，不影响流程

仓库规模跨度大，用三个档位承接，一套产品、一套表、一套流程：

| 档 | 日均作业行数 | 当班峰值人数 | 典型形态 |
|---|---|---|---|
| 小 | 500 行及以下 | 20 及以下 | 单班，一个管理者，收货与拣货不分队 |
| 中 | 501–10000 行 | 21–100 | 两到三班，设班组长，有专职复核与调度 |
| 大 | 10000 行以上 | 101–500 | 多班组多库区并行，管理分层，按库区分片作业 |

判定以**日均作业行数**为主口径（出库订单行为主，入库与加工按同口径折算），当班峰值人数与并发终端作交叉校验。两者矛盾时以作业行为准：人数是订单量的结果，不是原因。数值是初始口径，随首批仓实际数据校准。

档位可随业务变化调整。调档只改配置与部署规格，不动数据。

五条规则：

1. 档位只允许影响五项：Site 部署规格与并发目标（见 D54）、作业模式（见 D53）、任务指派策略（直接指派 / 班组派工 / 波次调度）、同一角色可开账号数（见 05）、看板汇总粒度。其余一律不得有差异。
2. 流程与模型不随规模变：单据流转、任务状态机、库存记账、计费口径、货主隔离在三个档位完全一致。小仓不得有简化流程。
3. 领域层不认规模：档位是策略层配置项，代码中不得出现按档位、按作业量或按人数选择的业务分支（与 D10 同源）。
4. 调档不改数据：调整档位不动库存模型、不迁移单据、不改历史记录。
5. 小仓不因规模小降低隔离：档位再小也是每仓一套 Site，不与其他仓共用（与 D08 同源）。

**否决**：小型仓独立产品线、按人数裁剪功能、把人数或档位写进单据与任务字段、小仓共用一套 Site 分摊成本。

### D53 作业模式按仓分两种，承载现场作业规范差异

5 人仓与 500 人仓的现场作业规范不一样，用两种作业模式承接，不用两套客户端：

| 模式 | 适用 | 现场形态 |
|---|---|---|
| 单人闭环 | 小档 | 一人从收货跟到发货，自己复核，单班，无交接 |
| 分工流水 | 中档、大档 | 按环节分岗、按库区或班组拆片，独立复核，班次交接 |

六类差异只允许用三种载体表达，不得各造一套流程：

| 现场差异 | 单人闭环 | 分工流水 | 载体 |
|---|---|---|---|
| 复核 | 收货人自检 | 独立复核人，不得与拣货同一人 | 人员约束 |
| 任务 | 整单指派，一人跟到底 | 按库区或班组拆片，多人接力（拆片维度见 D59） | 策略启停 |
| 拣货 | 按单拣 | 波次拣加集货位二次分播（集货位按 `SHIPPING` 类型库位建，不新增库位类型，见 D26） | 策略启停 |
| 交接班 | 无交接 | 每班交接未完结任务、异常与设备 | 单据（上一种模式自然为零张） |
| 盘点 | 全仓停业盘 | 分区循环盘点 | 默认参数 |
| 异常 | 就地找管理者 | 逐级上报 | 权限 |

四条规则：

1. 模式是仓级属性，建仓时选定，变更留痕。不做成藏在设置里的软开关——它决定独立复核这道错发防线是否成立。
2. 模式只改三类载体：策略启停、人员约束（相邻两步不得同一人）、默认参数。不改单据种类、不改状态机、不改库存记账、不改接口契约。
3. 关闭不等于删除：单人闭环下波次页仍可访问、仍受权限约束，只是没人用。代码中不得出现按模式选择的流程分支，只允许读配置项；作业端页面由当前任务类型驱动，不由模式驱动。
4. 两种模式各跑全链路用例：单人闭环必须能从收货一路走到发货，分工流水必须在没有独立复核时拦住。

**否决**：小仓版与大仓版两个客户端、按模式删页面或删单据、按规模加减状态与校验、把模式写进库存与任务表当业务字段。

### D55 单据、波次、任务三层常存，小仓靠聚合度退化

订单量小时，单据本身就是作业单位；订单量大时，单据一层撑不住，必须在单据与执行之间加一层聚合。这不是两套流程，是同一套三层结构在不同作业量下的退化：

| 层 | 作用 | 小仓 | 大仓 |
|---|---|---|---|
| 单据 | 履约凭证，对货主与计费的唯一口径 | 与任务一比一 | 一张单据由多张任务片共同完成 |
| 波次 | 拣货的聚合单位 | 一单一波，接单即开工 | 多单合波，按承运商、时效、库区聚合 |
| 任务 | 执行与库存锁定的单位，可拆片 | 整单一张任务 | 按库区拆片，多片并行，集货位合流 |

四条规则：

1. 波次是实体，不是视图。小仓不用「按单拣」绕过波次——一单一波即可，链路仍是同一条。做成视图就没有合波、拆片、合流的落点，大仓要重做。
2. 任务的主对象是任务片，不是单据。单仓端与作业端以任务进入作业；小仓看起来像按单作业，是任务与单据一比一的巧合，不得据此把单据做成作业主对象。
3. 小仓不允许「等波」：接单即派，不设订单池等待。只有大仓攒波，因为合波省下的行走与换库位成本大于等待成本。
4. 大仓不允许跳过波次直接按单派工：几百人同时抢同一批单，同一库位被多人同时拣，通道拥堵、互锁频发。合波是减少抢单冲突的手段，不是可选项。

**否决**：为小仓做「按单据作业」的独立模型、把波次做成报表视图、按人数决定是否建波次、小仓设订单池等待合波。

### D56 单据框架：两族、单头单行、五态，新增类型只加扩展表

所有单据共用一套单头与单行。不为每种业务各建一套表，也不做万能 JSON 单——JSON 行让数量、批次、唯一键与汇总无法用数据库约束保证。

**两族共用骨架，差异只在单行**：

| 族 | 面向 | 单行装什么 | 单据 |
|---|---|---|---|
| 履约单 | 货主与计费口径 | 货品要求：SKU、批次、要求数量、质量要求、包装要求、库区约束 | 入库通知单、收货单、出库单、调拨下行单 |
| 作业单 | 仓内操作指令 | 库位动作与库位对象 | 移库单、盘点单、加工单、冻结解冻单 |

分族的依据是单行是否必须带库位：履约单的库位由策略决定，作业单离开库位无法表达。两族共用单头与状态机。

**单头只装六组**：

| 组 | 内容 |
|---|---|
| 身份 | 系统单号、类型、来源、外部单号 |
| 归属 | 货主、仓库，均非空 |
| 时间 | 提交、受理、业务要求时间、完成 |
| 状态 | 商务态 |
| 关联 | 父单号、原单号 |
| 留痕 | 创建人、确认人、版本（乐观锁） |

单号在单仓端生成：类型前缀 + 仓编码 + 日期 + 当日序号。现场补录也要能出号，不依赖运营端协调。

**状态五态，所有类型同一套**：已受理 / 执行中 / 已完成 / 差异关闭 / 已取消。

三条硬规则：

1. 到货中、待上架一类进度不是单据状态，由收货单与任务反推，作列表辅助信息展示。
2. 不设「部分完成」终态：要么完成，要么人工确认后差异关闭，不允许单据长期悬空。
3. 状态只由任务事件推进，不接受前端直接改。

**四条边界**：

1. 一张单一个货主、一个仓，不跨。调拨拆成源仓出库单与目的仓入库单，用父单号关联。
2. 履约单的行不指定具体库位，只到库区或库位类型。
3. 单据不存人、设备、波次。波次成员关系记在成员表，不挂单头——挂单头，一张单就进不了第二个波次。
4. 单据不改库存，只产生任务（见 03）。

**履约数量是汇总值**：单行维护已履约数量与差异数量，由任务完成事件回写，不在单据里实时聚合任务表。理由是单据列表要按履约进度排序筛选，实时聚合会把列表拖死。日结核对汇总值与任务片之和。

**新增类型的成本固定**：加一个类型枚举 + 一张 1:1 类型扩展表（承运商、来源方式一类专有字段），不动单头单行、不动状态机、不改已有查询。专有字段不得塞进单头变成一堆可空列。验收标准：加一种单据若要改状态机或已有表结构，说明框架没定住。

**否决**：万能单据表 + JSON 行、每种单据各建一套表与状态机、类型专有字段塞进单头、单据上挂波次号或任务号。

### D57 作业要求按货品配置、单据行可覆盖，主流程不分叉

不同货主、甚至同一货主的不同货品，作业要求并不相同：有的货要贴标，有的不要；有的要登记批次与序列号，有的不记。这类差异用**作业要求项**表达，不用流程定义表达。

主流程只有一条：收货 → 上架 → 在库 → 拣货 → 复核 → 发货。货主差异不产生第二条链路，也不出现按货主切换的单据状态机。

**差异的四种形态，各归各的落点**：

| 差异 | 归到哪里 | 依据 |
|---|---|---|
| 某类货多一道加工（贴标、换包装、组合拆包） | 生成一张加工单（作业单），插在主流程的入库侧或出库侧；两侧都开时各生成一张 | D44、D56 |
| 某类货要记批次或序列号 | 库存唯一键与单据行字段 | D29 |
| 某类货必须独立复核 | 人员约束：拣货人与复核人不得同一人 | D53 |
| 某类货允许不经存储直接发运 | 越库，走 03 的显式例外机制 | 03 |

**作业要求项按四级继承，粒度落在货品**：

```
单据行显式指定  >  货品作业要求  >  货主默认  >  仓库默认
```

五条规则：

1. **就近覆盖，不是或运算**：某一级有显式值时以该级为准，其余层不再参与判断。四层都没有配置则视为不作要求。
2. **货主级只是默认值**：它让新货品免于逐个填写，不是硬规则。同一货主的不同货品可以取相反的值——这正是必须把粒度落在货品的理由。
3. **单据行是本次例外**：只对本次单据生效，不回写货品主数据。临时加贴英文标走这里，不改档案。
4. **一处配置决定三件事**：是否生成加工单、作业端是否出现对应任务、是否产生计费事实。三者同源，不允许各配一遍。
5. **入库贴标与出库贴标是两个独立开关**：可同时开启，也可以只开一个，不存在互斥。同一次作业在两个环节各生成一张加工单，各记各的在制与计费。贴什么标（标签模板、语言、条码规格）不进要求项，由加工单的行指定——要求项只回答「这一步要不要贴」。两侧都开时，两处是否贴同一张标由货主决定，WMS 不判断标签语义、不自行去重。

**作业要求项清单（首期）**：

| 要求项 | 取值 | 有它时多出什么 |
|---|---|---|
| 入库贴标 | 关 / 开 | 收货后生成加工单，货进在制工位再上架；产生计费事实 |
| 出库贴标 | 关 / 开 | 拣货后生成加工单，货进在制工位再发货；产生计费事实 |
| 批次管理 | 关 / 开 | 收货必须登记批次，库存按批次分行 |
| 序列号管理 | 关 / 开 | 逐件登记序列号 |
| 独立复核 | 关 / 开 | 拣货与复核不得同一人 |
| 越库直发 | 关 / 开 | 不经存储位，收货后直接进发货位 |

**不做**：

1. 不做流程编排：不提供节点拖拽、条件分支、脚本。状态机与不变量是硬约束，一旦可编排，数据库约束、分层校验与 INV 系列全部失去落点；计费事实也无法确定一单实际发生了哪几道工序。
2. 不做货主专属流程版本：那是给货主开特权分支，撞 D03。能力同构不等于配置相同——所有货主用同一套要求项，只是取值不同。
3. 不在代码里按货主判断：差异只能是数据，领域层只读配置（与 D10 同源）。

**否决**：按货主编排流程、按货主切换单据状态机、把作业要求写成代码常量或按货主的枚举分支、为「要贴标的货」单独建一套单据类型。

依据 D03、D10、D29、D44、D56。

## 3. 部署架构

### D06 三级部署

| 层 | 面向 | 部署位置 | 职责 |
|---|---|---|---|
| Open Platform | 外部货主 | 云上公网区 | 货主门户、开放 API、Webhook |
| Hub（运营管理端） | 内部员工 | 云上私网区，每法域一套 | 权威主数据、合同费率、统一视图、跨仓调度、计费出账 |
| Site（单仓执行端） | 现场作业员 | 云上私网区，每仓一套 | 库存真值、库位、任务、收发存、加工、设备 |

### D07 Hub 按法域分区，跨境只传摘要

中国区 Hub 管中国仓，美洲区 Hub 管美洲仓。两个 Hub 之间只交换摘要（库存总量、单据状态、调拨进度），**明细不出境**。

### D08 每个仓一套独立部署，不是断网自治

Site 每仓一套：独立容器工作负载、独立数据库、独立资源组，库存真值只在本仓实例。全部部署在云上，以容器交付，仓内不设机房，现场只保留移动作业端（PDA 或手机）与采集终端。**依赖网络是前提，不是缺陷**，不考虑断网作业。

自治的三条理由：法域与数据主权、就近区域的现场延迟、故障与升级隔离。

Site 的云区域与仓所在城市同城或同区域。跨区域集中部署等于放弃第二条理由，须先改本条。

**否决**：Site 与 Hub 共用一个集群、共用一个主库；多个仓共用一个 Site 实例。

### D09 模块化单体，不用微服务

WMS 的核心资产是库存准确性；库存扣减、任务分配、库位锁定必须同事务完成。拆微服务需引入 Saga 与补偿，直接后果是差账。

首期：模块化单体 + 主库 + Redis + MQ。模块间只通过应用服务调用，不共享表。

**否决**：微服务、分布式事务、最终一致的库存。

### D10 领域层不认仓型，差异全在策略层

- 领域层只守护不变量
- 仓型能力矩阵、上架/分配/波次规则、费率规则全部在策略层以配置表达
- 判断标准：新增一个仓型时若需改领域层代码，说明架构切错

### D59 作业策略参数归单仓端，运营端只读

作业策略参数决定现场怎么干活：波次按什么合、任务按什么拆、怎么派工、上限与开关怎么定。每个仓的库区布局、人手、设备、货主结构都不同，只有现场知道怎么配。放运营端有两个后果：调整要跨端审批，滞后于业务；配出来的规则现场不用，最后还是靠口头指挥。

| 内容 | 权威源 | 运营端 |
|---|---|---|
| 作业策略参数（聚合规则、拆片维度、派工方式、上限与开关） | 单仓端，仓级 | 只读 |
| 仓型能力矩阵 | 运营端，随仓库档案下发 | 写 |
| 策略实现类装载 | 单仓端 | — |

四条规则：

1. 建仓时按仓型生成初始默认值，不让运营端逐仓手填；单仓端接手后可改。
2. 变更只影响之后新产生的波次与任务；已受理单据与已生成任务不回溯（与 D53 同源）。
3. 运营端不得以统一策略名义下发覆盖；跨仓一致只能靠仓型能力矩阵与初始默认值。
4. 变更留痕：改哪项、原值、新值、原因、操作人。

**否决**：运营端下发作业策略、跨仓强制统参、把作业策略参数并进仓库档案下发。

### D60 库存只记两个数量，冻结靠状态行表达

库存数量只有两个字段：`qty_on_hand`（在库）与 `qty_allocated`（已分配未执行）。**不设 `qty_frozen`**。

冻结与隔离靠「状态行」表达：`stock_status` 在唯一键里（D29），冻结是把库存从 `AVAILABLE` 行转到同库位的 `FROZEN` 行——是行间转移，不是字段增减。

| 概念 | 怎么算出来 |
|---|---|
| 可用量 | `status=AVAILABLE` 行的 `qty_on_hand − qty_allocated` |
| 冻结量 | `status=FROZEN` 行的 `qty_on_hand` 之和 |
| 隔离量 | `status=QUARANTINE` 行的 `qty_on_hand` 之和 |

好处是唯一键天然约束，不会出现「数量字段与状态不一致」；代价是查冻结量要按状态汇总，不能读单行。

**否决**：同一行放 available / locked / frozen 多个数量字段。那种建模要靠额外的恒等式校验保证几个数加起来等于总量，而我们已经把这一层交给唯一键与数据库约束。

### D11 一致性分层

| 域 | 一致性 | 手段 |
|---|---|---|
| 库存 / 库位 / 分配 | 强一致 | 单库事务 + 行锁 |
| 任务状态 / 指派 | 准实时 | 乐观锁 / Redis 原子操作 |
| 计费 / 账单 | 最终一致 | 独立计费域，事件驱动，可重算（见 D49） |
| 报表 / 看板 | 最终一致 | 异步汇总 |

### D54 单仓容量以并发终端为口径，超上限先升规格再谈拆仓

容量规划的单位是并发在线终端数，不是人数：移动作业端一人一台（PDA 或手机），固定式采集站多人共用，两者不成正比。

| 项 | 小档 | 中档 | 大档 |
|---|---|---|---|
| 并发在线终端 | ≤ 20 | 21–120 | 121–500 |
| Site 应用副本 | 1 | 2 | 3 起，按压测定 |
| Site 数据库 | 最小规格单实例 | 中规格，每日全量 + 持续归档 | 高规格，持续归档 + 只读副本 |
| 任务池与扫码热数据 | 与 Hub 共用 Redis 实例的独立库 | 独立 Redis 实例 | 独立 Redis 实例，按用途分库 |

四条规则：

1. 上表是规划基线，不是承诺值。每档上线前按目标并发终端数压测，未达标不验收该档仓库。
2. 应用多副本的前提是任务领取、库位锁定走数据库行锁或 Redis 原子操作，不得放在进程内存里；否则加副本就破坏一致性（与 D11、D30 同源）。
3. 单仓超过大档上限时，先升规格重压测；升到顶仍不够，才评估把该仓按库区拆成两个 Site——这会推翻 D08 的一仓一套，必须先改本条与 D08，并把跨片移库、分片盘点的代价写清楚。
4. 并发目标不写进业务表，只出现在部署配置与压测报告里。

**否决**：用人数按固定比例换算并发终端、超上限继续硬撑、多仓共用一套 Site 分摊压力。

## 4. 数据归属

### D12 主数据权威源唯一

| 实体 | 权威源 | 流向 |
|---|---|---|
| 货主、SKU、角色权限 | Hub | 下行缓存到 Site |
| 员工档案（含可作业资格） | Site，仓内 | 单仓端建档与改档，上行到 Hub 作副本（见 D62） |
| 账号与角色授予 | Hub | 账号库在 Hub；单仓端受限开通账号并授予本仓角色（见 D62、19） |
| 合同、费率卡、计费规则 | 计费域 | 生效状态下行缓存到 Site，供作业校验 |
| 库位、库区、库存、任务 | Site | 上行到 Hub 作副本 |
| 仓内单据（入库通知单、收货单、出库单、移库单、盘点单、加工单） | Site | 上行到 Hub 作副本；货主端与运营端是同一张单的视图，不是另一张单 |
| 作业策略参数（聚合规则、拆片维度、派工方式、上限与开关） | Site，仓级 | 运营端只读（见 D59） |
| 设备型号能力字典 | Hub | 下行 |
| 设备实例 | Site | — |
| 跨仓调拨单 | Hub 创建 | 下行到源仓与目的仓 |
| 仓库档案、仓型 | Hub | 下行缓存到 Site |
| 仓库作业日历 | Site | 上行到 Hub 作副本 |
| 班组、班组归属、班组职务、临时支援 | Site，仓内 | 上行到 Hub 作副本（见 D60） |

规则：每个实体只有一个权威源，非权威方只读。同一实体的不同字段段可以有不同权威源，但必须在上表逐段列出，不得含糊。

单据只有一份：归属单仓端，一个单号、一个状态，单号在单仓端生成（现场补录也要能出号，不依赖运营端协调）。货主提交的外部单号另存一列，只作幂等与对账。货主端是提交入口与只读视图，可见性由数据域决定，不靠副本表。

`warehouse` 是单仓执行端的根对象：库区、库位、库存、任务、单据全部挂在它下面，`warehouse_id` 必含且非空。它不参与货主隔离——同一仓可以服务多个货主，隔离靠 `owner_id`（见 D02）。

### D60 班组是仓内作业组织，不是权限组织

班组是现场作业的分工单位，用来派工、点人、看进度、追责任。它不是部门，不是汇报关系，也不是权限主体。

| 项 | 规定 |
|---|---|
| 层级 | 仓下最多三层，不建跨仓组织树 |
| 归属 | 一人同一时刻只有一个主属班组，历史归属保留 |
| 职务 | 班组长、副组长、成员，记在归属记录上，随调组失效 |
| 鉴权 | 班组不进入角色与数据域；班组事务权按职务在应用层校验 |
| 删除 | 只停用与归档，不物理删除（与 INV-18 同源） |
| 权威源 | 班组、归属、职务、员工档案归单仓端；账号与角色归 Hub |

五条规则：

1. **班组树只表达作业分工**，不表达汇报关系，深度不超过三层。更深的层级属于人事组织架构，WMS 不建。
2. **班组职务不是系统角色**：账号角色仍只有单仓管理者与现场作业员（见 05），班组长不新增角色枚举。
3. **班组长只能管理本组直属成员的事务**，可查看本组与子组；跨组操作一律拒绝，不靠前端隐藏。
4. **班组不设人数上限**，也不作为库存、单据、任务的归属字段；任务只引用执行人，不引用班组。
5. **班组不进入数据域**：05 与 19 的数据域仍只有货主与仓两个维度，不为班组增加第三维。

**否决**：把班组做成部门树或汇报关系、为班组新增角色枚举、给班组加数据域维度、把班组写进单据与库存表、班组物理删除。

### D61 人员状态只有登录与未登录，不做考勤与排班

人员状态不建模成请假、缺勤、在岗、离岗，只回答一件事：这个人当前是否登录。系统不做考勤，也不排班。

| 层 | 管什么 | 权威 | 取值 | 影响 |
|---|---|---|---|---|
| 任职 | 是否在职 | Site 员工档案（见 D62） | 在职 / 离职 | 能否入组、登录 |
| 账号 | 能否登录 | Hub 权限域 | 启用 / 停用 | 能否登录 |
| 归属 | 在哪个班组 | Site 班组归属 | 在组 / 已调出 | 能否被派工 |
| 登录 | 当前是否登录 | Site 会话 | 已登录 / 未登录 | 当前能否被派工 |

可作业资格是能力标记，记在 Site 的人员作业档案上，取值正常、限制、禁止，由单仓管理者维护。它不是考勤状态，也不是第五种人员状态。

五条规则：

1. **人员状态只有登录与未登录**：登录成功即已登录；主动退登、会话超时、账号停用、离职即未登录。不设请假、缺勤、在岗、离岗。
2. **不做考勤与排班**：不算工时、不排班、不做请假审批、不算薪。需要这些能力时由外部人事系统承担，WMS 不接。
3. **登录不等于在工位**：系统只回答「当前是否登录」，回答不了「是否在工位」；现场是否在工位由班组长看人，不由系统造一个状态。
4. **登录状态不落业务表**：由会话服务派生，名单查询批量取；不建状态表、不写状态流水，避免双份状态不同步。
5. **可派工不存布尔值**：由任职、账号、归属、已登录、资格五项实时组合判定，班组停用视同不可派工，任务侧再排除有进行中任务的人，任何一项变化立即生效。

**否决**：请假、缺勤、在岗与离岗、排班、工时、考勤报表、请假审批、人员状态表与状态流水、把登录时长当考勤。

### D62 员工档案归单仓端，管理岗是角色不是档案类别

现场员工在当地招聘，档案由单仓端建档、改档、离职；管理岗不是另一类档案，而是持单仓管理者角色的员工。运营端不建仓内员工档案，只授全局治理角色。

| 项 | 规定 |
|---|---|
| 档案 | 本仓全部员工一份档案，归 Site；不按作业岗与管理岗拆两份 |
| 管理岗 | 持单仓管理者角色；角色收回即不再是管理岗 |
| 账号 | 账号与角色归 Hub；单仓端可开作业账号、授本仓管理角色 |
| 员工号 | 仓编码加四位序号，单仓端生成，全局唯一 |
| 跨仓 | 首期不做人员调仓；原仓离职、新仓入职 |
| 运营端 | 只读员工副本；授计费、对账、跨仓调度、权限管理员角色；不建档案 |
| 离职 | 单仓端办理；置离职、停账号、结束归属、失效会话 |

七条规则：

1. **员工档案只有一份，归单仓端**；不设岗位类别字段，管理岗由角色派生。
2. **单仓端可授现场作业员与单仓管理者角色**，限本仓；不得授予计费专员、对账员、跨仓调度员、权限管理员。
3. **不能给自己授权**；免职最后一个单仓管理者前必须先授另一个，至少保留一个可用管理者。离职导致管理者为零时，由运营端权限管理员补授。
4. **账号仍由 Hub 统一持有与鉴权**：单仓端通过受限接口开通账号与授予角色，不直接写权限库。
5. **员工号由单仓端生成**，格式为仓编码加四位序号；仓编码全仓网唯一（D41），因此员工号全局唯一。
6. **跨仓人员流动首期不做调仓单**：按原仓离职、新仓入职处理，员工号在新仓重新生成，历史在各自仓保留。
7. **离职不删档案**：置为离职、停用账号、结束班组归属、失效会话，进行中任务先改派。

**否决**：把管理岗做成档案类别或岗位字段、按作业岗与管理岗拆两份档案、运营端代办现场建档、单仓端授予计费或权限角色、自授管理角色、跨仓直接改所属仓、离职物理删档案。

### D13 事实下沉，计算上收

作业事实（计费事件）在 Site 产生；计费计算与出账在 Hub，因为一个货主可能跨多仓需要合并出账。

### D14 跨仓调拨无在途库存

调拨 = 源仓出库 + 目的仓入库，两段各自本地执行。源仓发运即减库存，目的仓收货前库存不存在。

**否决**：建"在途仓"作为库存容器。在途属于物流段，不归 WMS 记账。

## 5. 客户端与接入

### D15 四个客户端，一套 API 契约

| 端 | 载体 | 面向 | 部署位置 |
|---|---|---|---|
| 运营后台 | Web (PC) | 内部员工 | Hub |
| 货主端（货主门户） | Web | 外部货主 | Open Platform |
| 单仓端（含固定式采集站） | Web，触摸屏与采集站 | 单仓管理者、现场作业员 | Site |
| 移动作业端 | Android 原生，同一 App 覆盖工业 PDA 与普通安卓手机 | 现场作业员 | Site |

PDA 与手机不是两个端：同一个 App、同一版本、同一套接口，差别只在硬件能力（见 D58）。凡按机型写的业务分支，都算多造一个端。

固定式采集站不是独立端，是单仓端在收货台、复核台的固定安装形态；四端与 05 的角色总览一一对应。

接入层只做认证、限流、路由、协议转换四件事，不得自拼 SQL 或绕过业务校验。

### D16 移动作业端是独立工程，但在线终端

技术栈、发布节奏、硬件 SDK（扫码/打印/蓝牙秤/RFID）均独立于后台。同一套 App 装在工业 PDA 与普通安卓手机上：PDA 走扫码头，手机走摄像头；有无物理扫描键、打印、电子秤、RFID 以设备能力声明为准。

不考虑断网，因此**不做**：本地数据库、任务队列、同步引擎、冲突处理、业务规则端上快照。

保留：请求超时重试、幂等、明确失败提示（应对 WiFi 漫游抖动）。

**否决**：移动作业端离线执行、业务规则双份。

### D17 货主只面对一个入口

统一域名、统一 AppKey、统一错误码。货主不感知仓库部署位置与 Site 数量。

### D18 外部流量与作业流量物理隔离

Open Platform 独立部署、独立资源池、独立限流。Hub 下行到 Site 的指令走队列，不穿透为同步调用。移动作业通道优先级高于任何外部请求。

理由：客户 ERP 批量推送打挂仓库系统是真实事故。

### D19 查询分两类路由

| 类型 | 走向 |
|---|---|
| 单仓实时可用量 | 透传 Site，短超时；失败降级为 Hub 副本但必须带数据时间戳 |
| 跨仓聚合、历史流水、报表 | 走 Hub 副本 |

### D20 写入一律异步受理

提交单据 → 立即返回受理号；状态靠 Webhook 主动推送 + 查询接口兜底。

### D21 幂等做在入口

所有写入 API 必须带外部单号，接入层以其为幂等键去重，重复提交返回首次结果，不下发到 Site。

## 6. 设备管理

### D22 设备只管"作业终端"，不做资产管理

管：设备台账、身份绑定、能力（扫码头/摄像头/物理扫描键/RFID/打印/低温/防爆）、运行状态（在线/电量/App 版本）。

不管：采购、折旧、维修工单、固资盘点（属 EAM）。

### D23 设备激活时一次性绑定，登录不扫设备码

- 设备**身份注册**：激活时一次性绑定 SN 与设备密钥，写入台账
- 员工**登录**：只验员工身份（账号/员工码 + PIN）

**否决**：每次登录扫机身码（App 本就知道自己在哪台设备上，冗余）。

防"非登记设备登录"靠三层：受管分发/MDM、每台设备独立密钥、Site 侧设备白名单校验。现场终端走公网接入云端 Site，没有仓内网这道边界。

### D24 操作留痕三元组

`人 + 设备 + 库位`。靠会话数据获得，不靠员工扫码。换班必须退登，超时自动退登。

### D25 必须每次扫的是库位码、SKU 码、批次码

扫码是混存场景下的防错主手段。手工录入只能是例外，且必须打标记留痕。

扫码校验放服务端，靠三项保证反馈速度：单条轻量接口、校验数据预热到 Redis、连接复用。

### D58 扫码通道按设备能力选，不按终端类型分叉

设备能力字典把扫码拆成「扫码头」与「摄像头」两项，并单列「物理扫描键」（D22）。App 启动时读取当前设备的能力声明，据此选扫码通道：有扫码头走扫码头，只有摄像头走摄像头。两条通道都是主路径，都受 D25 的服务端校验约束。

界面不得依赖物理按键，也不得假定摄像头一定可用。设备台账区分 PDA 与手机，只用于台账与选型，不进入业务规则；按「PDA / 手机」写的业务分支算规则双份。

## 7. 库位与库存模型（草案已定，待正式成文）

### D26 禁止虚拟库位

`location.loc_type` 枚举不含 `VIRTUAL`。九种真实物理类型：`STORAGE / RECEIVING / SHIPPING / DOCK / QC / QUARANTINE / WIP / RETURN / SCRAP`。

待检、隔离、在制、报废全部是真实库位，不是虚拟仓。

### D27 库存状态与位置正交

- **改状态不动位置**：可用 → 冻结，原地不动
- **移位置不改状态**：存储位 → 隔离位

两者是独立操作，分别留痕，不能合并成一个"库存调整"。

### D28 库位必须有四段物理坐标才可启用

`aisle_no / rack_no / level_no / bin_no` 非空；`verified_at` 记录最近一次现场指认时间。库位状态只有 `ENABLED / DISABLED / MAINTENANCE`，**没有"占用/空闲"**（混存后占用是渐变量，必须实时计算）。

### D29 库存唯一键七字段

`(owner_id, location_id, container_id, sku_id, batch_no, stock_status, serial_no)`

`serial_no` 与 `container_id` 都必须 `NOT NULL DEFAULT ''`——联合唯一索引中 NULL 不参与去重，留空会产生重复库存行。空串 `container_id` 表示散货（无容器，直接地堆或上架）。

库位始终是唯一锚点：库存的 `location_id` 非空；容器是中间层，可空，且容器有位置时必须与库存位置一致。

### D30 混存容量核算含已分配未执行

```
库位占用 = Σ 在库换算占用 + Σ 已分配未执行换算占用
上架可用 = 物理上限 − 库位占用
```

上架选址必须事务内 `SELECT ... FOR UPDATE` 锁库位行。

### D31 强制手段三层

| 层 | 职责 |
|---|---|
| DB | `location_id NOT NULL` + FK、`loc_type` CHECK、`qty_allocated <= qty_on_hand`、七字段唯一键、坐标非空 |
| 应用 | 库存写入只走 `StockService`；库位启用前校验坐标；上架加锁；货主数据域注入 |
| 核对 | 库存 vs 流水日结、库位禁用仍有库存告警、超容扫描、库位码现场指认校验 |

## 8. 计费

### D32 合同挂在货主上，费率差异用维度表达

合同是货主与仓网运营方之间的唯一价源，主体是 `owner`，**不挂仓库**。一个货主一份合同，覆盖全仓网。

同一货主在不同仓型、不同仓、不同库区的费率差异，通过费率卡的适用维度表达（仓型 / 仓库 / 库区 / 服务项），不拆成多份合同。

**否决**：按仓签合同、`owner_warehouse` 作为合同主体、一个货主多份并行合同。

### D33 无生效合同不可作业

入库受理前校验该货主存在生效期内的合同版本。硬拦，不是警告。

校验对象是**货主**，不是「货主 + 该仓」：合同全仓网通用，不按仓判断准入。

### D34 合同版本化，按事实发生日匹配

改价 = 新建版本，历史版本只读。计费不能用"当前合同"回算历史作业。

### D35 取整规则写进合同配置

不足一托按一托、按天/按小时、不满一月按整月、阶梯累进还是全额跳档——不得硬编在代码里。

### D36 计费明细只能冲正，不能改

`charge_detail` 禁止 UPDATE/DELETE。修正 = 反向明细 + 新增明细，必须成对。

### D37 每笔金额必须可回溯

明细固定结构含：事实流水 ID + 合同版本 + 规则快照 + 计算参数。缺一不可。

### D38 跨时区日切按仓所在法域

时间戳统一存 UTC；"按天计费"的日切点按仓库所在法域时区，且必须在合同中写明。

### D39 计费权限独立于作业岗

计费专员（维护合同费率）、对账员（核账出账）与仓库作业岗彻底分离。作业的人不能改价格。

## 9. 全局不变量

| 编号 | 不变量 | 强制手段 |
|---|---|---|
| INV-01 | 所有库存必须绑定真实物理库位（`location_id NOT NULL` + FK + 无 VIRTUAL 枚举） | 数据库约束：非空 + 外键 + 库位类型枚举无虚拟值 |
| INV-02 | 库位必须有物理坐标才可启用，且需能在现场被指认 | 数据库约束：启用态四段坐标非空；应用校验：启用前扫码一次并留痕 |
| INV-03 | 库存流水的 `to_location_id` 永远非空；`from_location_id` 仅"外部→库内"事件可空 | 数据库约束：非空 + 事件类型 CHECK |
| INV-04 | 库位容量不可超占（含已分配未执行） | 应用校验 + 库位行锁：分配与上架同事务内校验 |
| INV-05 | 独占库位（`mixed_policy=EXCLUSIVE`）不得混货主 | 应用校验 + 库位行锁；日结核对混货主库位 |
| INV-06 | 货主是唯一隔离维度，不可绕过 | 应用校验：仓储层统一注入货主条件，禁止手写；越权测试 |
| INV-07 | 批次、序列号、容器不跨货主合并 | 数据库约束：唯一键含 `owner_id` |
| INV-08 | 分配只增 `qty_allocated`，不改变库存状态；`qty_allocated <= qty_on_hand` | 数据库约束：分配量不超过在库量；应用校验：分配不写状态字段 |
| INV-09 | 库存变动必留事务，事务不可改、不可删；日结库存与流水对账 | 账号权限：流水表只授 INSERT；定时核对：日结比对余额与流水 |
| INV-10 | 任务拆片携带已锁定库存切片，不重新分配；结案时校验分片之和 = 父任务分配量 | 应用校验：结案事务内校验分片之和 |
| INV-11 | 已分配未执行的库存不得被他人上架挤占 | 应用校验 + 库位行锁：与 INV-04 共用同一把锁 |
| INV-12 | 无生效合同不可作业 | 应用校验：受理前硬拦；Site 侧合同缓存缺失即拒绝作业 |
| INV-13 | 计费按事实发生日匹配合同版本 | 应用校验：按事实时间戳选版本；版本边界用例测试 |
| INV-14 | 计费明细只能冲正，不能修改 | 账号权限：明细表不授 UPDATE 与 DELETE |
| INV-15 | 每笔金额可回溯至事实 + 合同版本 + 规则 | 数据库约束：事实流水、合同版本、规则快照、计算参数四个字段非空 |
| INV-16 | 在制库存必须落在真实工位库位，禁止"在制池" | 数据库约束：`location_id` 非空；应用校验：库位类型为工位 |
| INV-17 | 加工投入 − 产出 − 损耗 ≈ 0，损耗必须有去向 | 应用校验：完工事务内平衡校验；容差按计量单位在策略层配置 |
| INV-18 | 数据不物理删除 | 账号权限：业务表不授 DELETE；表设计：逻辑删除标记 |
| INV-19 | 权限双重校验：功能权限 + 数据域权限 | 应用校验：统一鉴权切面；越权用例测试 |

## 10. 被否决的替代方案汇总

| 否决项 | 理由 |
|---|---|
| 租户 Tenant | 系统无此概念，隔离维度只有货主 |
| 内部货主 / 内部结算价 | 所有货主同构，差异只在合同 |
| 虚拟库位 / 逻辑库位 / 在途仓 / 在制池 | 违反核心不变量 |
| 微服务架构 | 库存需强一致，拆服务会导致差账 |
| Site 与 Hub 共用集群 | 跨国部署不可行（法域、延迟、故障隔离） |
| 多个仓共用一个 Site 实例 | 一仓故障波及他仓，库存真值的边界不再是仓 |
| 移动作业端离线执行 | 不考虑断网，离线能力是多余复杂度 |
| 按 PDA / 手机分两套 App 或两套流程 | 同一个端同一套功能，差异只在硬件能力（D58） |
| 业务规则端上双份 | 不考虑断网后，规则单份在服务端 |
| 登录时扫设备码 | App 本就知道设备身份，冗余 |
| 用库存状态表达位置 / 用位置表达状态 | 两维度必须正交 |
| 把库位占用做成状态字段 | 混存后占用是渐变量，会互相覆盖 |
| 货主—仓库白名单 / 按仓开通 | 货主开通即全仓网可见；作业准入由合同校验，不需要仓级授权 |
| 按货主编排作业流程 / 货主专属流程版本 | 货主差异用作业要求项表达，主流程只有一条（见 D57） |
| 把班组做成权限角色 / 数据域维度 | 班组随归属走，权限随账号走；加班组维度会让调组后的权限无法自动回收（见 D60） |
| 请假、缺勤、在岗离岗、排班与工时 | 人员状态只有登录与未登录；WMS 不做考勤，也不替人事系统造状态（见 D61） |
| 把管理岗做成档案类别 / 运营端代办现场建档 | 员工档案只有一份，管理岗由角色派生；招聘与离职都在当地，运营端只管全局治理角色（见 D62） |
