# 仓型能力矩阵

仓型只有楼层仓与平面仓两种，差异集中在垂直空间、货架形态、搬运设备、作业动线四个维度，全部以「能力项」配置表达；业务代码读能力项，不读仓型枚举。

---

## 问题

**解决**：定住两种仓型的差异维度、差异怎么表达（能力项而非分支）、能力项从哪来、新增仓型怎么扩、哪些差异不该进领域层。

**不解决**：具体数值（层高、承重由每个仓的档案填写）、库位模型（见 04）、作业策略参数（归单仓端，见 D59）、设备型号选型。

---

## 设计

### 差异只有四个维度，其余都是配置

| 维度 | 楼层仓 | 平面仓 | 表达载体 |
|---|---|---|---|
| 垂直空间 | 层高受限，通常 4 ~ 6 米 | 层高充足，通常 8 ~ 12 米 | 仓库档案的层高字段（D42） |
| 货架形态 | 轻型货架或地堆，2 ~ 3 层 | 高位货架，4 ~ 5 层 | 库位类型与库位容量 |
| 搬运设备 | 地牛、电动托盘车、货梯 | 前移式叉车、平衡重叉车 | 设备能力字典（D22） |
| 作业动线 | 楼层间靠货梯，动线短、通道窄 | 单层平面，动线长、通道宽 | 拣货路径策略（策略层） |

层高区间是行业常见值，**不是本项目实测数据**；每个仓的真实层高以仓库档案为准。

四个维度之外没有第五个。如果新出现一种差异，先判断它能不能归到这四个里，不能就先别急着建字段——多半是策略参数或设备能力，不属仓型。

### 层高是硬约束，直接卡库位高度上限

依据 D42：层高决定货架可建高度与库位高度上限。

```
库位可用高度 = 层高 − 梁下净空余量
库位高度 ≤ 库位可用高度
```

| 环节 | 校验 |
|---|---|
| 建库位时 | 库位高度超过可用高度则拒绝创建 |
| 上架时 | 商品含托盘高度超过库位高度则拒绝选址 |
| 改装货架时 | 重新校验该库区所有库位 |

这条是两种仓型最实质的差异：同一个商品能上 4 层高位货架，在楼层仓可能只能地堆两层。

### 差异用「能力项」表达，业务代码不判断仓型

能力项清单（首期）：

| 能力项 | 类型 | 影响什么 |
|---|---|---|
| 最大库位高度 | 数值 | 库位创建与上架校验 |
| 单库位最大承重 | 数值 | 上架校验 |
| 是否存在多层 | 布尔 | 是否产生货梯任务 |
| 可用搬运设备类型 | 集合 | 任务分配时过滤设备 |
| 通道最小宽度 | 数值 | 大件商品的库位可用性 |
| 是否需要货梯转运 | 布尔 | 跨层移库时插入货梯任务 |

判断标准的写法对照：

| 错误写法 | 正确写法 |
|---|---|
| `if (warehouseType == 楼层仓) { 用货梯 }` | 读能力项 `needElevator`，为真则插入货梯任务 |
| `if (warehouseType == 平面仓) { 用叉车 }` | 读能力项“可用搬运设备”，按设备集合匹配 |
| `switch (warehouseType)` 出现在业务包里 | 业务包不出现仓型枚举比较（AR-10 会拦） |

关键点：**领域层拿到的是能力值，不是仓型**。仓型只在建仓时用来生成初始能力值，之后就不再参与任何判断。

### 能力项由运营端维护、随仓库档案下发

依据 D59 的权威源表：

| 内容 | 权威源 | 谁可写 |
|---|---|---|
| 仓型能力矩阵（本表） | 运营端 | 运营端维护，随仓库档案下发 |
| 具体仓的能力值 | 单仓端，仓级 | 单仓端可覆盖 |
| 作业策略参数 | 单仓端，仓级 | 单仓端（与能力值分开） |

流程：

```
建仓时选仓型 → 生成一套默认能力值 → 下发到单仓端 → 单仓端按实际情况覆盖
```

建仓时按仓型生成初始默认值，不让运营端逐仓手填；单仓端接手后可按实际货架、设备调整。

### 新增仓型只加一个枚举值加一套默认值

| 步骤 | 内容 |
|---|---|
| 1 | 加一个仓型枚举值 |
| 2 | 加一套默认能力值模板 |
| 3 | 不动领域代码、不改库位模型、不加业务分支 |

验收标准：新增仓型如果要改 `domain` 包里的代码，说明切错了（D10）。

这条目前只有两个值，看起来多余，但它决定了以后加第三种仓型（比如自动化立库）时的成本。立库进来时，能力项里会多出“是否需要堆垛机”“是否有提升机”这类，但领域层仍然只读能力值。

### 楼层仓独有的瓶颈是货梯，要在设备侧排队

货梯是共享资源，一次只能运一托，是楼层仓独有的**受限资源**。

| 项 | 做法 |
|---|---|
| 建模 | 货梯在设备台账里登记为受限资源（类型：垂直运输） |
| 排队 | 跨层任务需要申请货梯时段，按任务优先级排队 |
| 容量 | 一次一托，超重或超大拒绝 |
| 故障 | 货梯停用时，跨层任务暂停并告警，不自动改走楼梯 |

平面仓没有这个对象，但代码里不需要判断“是不是楼层仓”——只要该仓的能力项里有“是否需要货梯转运”且有货梯设备，排队机制就生效；没有就不生效。

### 平面仓独有的问题是动线长，靠库区划分与路径策略

平面仓通道宽、面积大，行走距离是主要成本。

| 手段 | 归属 |
|---|---|
| 库区划分（按周转率分区） | 库位模型（见 04） |
| 拣货路径排序 | 策略层（D59 归单仓端） |
| 波次聚合按作业区 | 17 波次模型 |

这三件都不属仓型能力矩阵，本文只说明“平面仓的差异体现在这里”。

## 约束与验证

| 约束 | 强制手段 |
|---|---|
| 业务代码不得判断仓型 | 构建期：CI 关键字扫描，业务包内出现仓型枚举比较即失败（AR-10，见 14） |
| 库位高度不得超过层高 | 应用层：建库位与上架时校验；数据库层：库位高度非空且大于零；核对层：日结扫描超限库位 |
| 能力项必须有默认值 | 应用层：建仓时按仓型生成，缺默认值拒绝建仓 |
| 能力值变更留痕 | 数据库层：改前值、改后值、操作人、原因四项非空 |
| 能力值只影响新建 | 应用层：变更只对新产生的库位、任务、波次生效，已生成的不回溯（与 D53 同源） |
| 新增仓型不改领域代码 | 构建检查：新增仓型只允许改枚举、默认值模板与配置，`domain` 包改动需单独说明 |

引用的决策编号：D10、D22、D42、D53、D59；模块归属见 03 M10 与 M09，库位与容量见 04，波次与路径见 17。

具体层高、承重、设备型号不在本文范围：那是每个仓的档案数据，不是设计结论。
