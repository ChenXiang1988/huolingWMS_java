# 开源 WMS / WES 调研方法与报告模板

本文件先于所有报告定稿，用于约束后面每一份报告"能写什么、不能写什么"。

---

## 1. 本批调研要回答的问题

只回答四个问题：

1. 这个项目**实际有什么**（代码、表、模块、接口）。
2. 它**用什么技术实现**（构建文件里的版本号，不是宣传口径）。
3. 它**怎么跑起来**（部署文件、脚本、依赖组件）。
4. 对我们**可以拿哪一块**（必须指到具体文件或表名）。

不回答：哪个项目"更好"、社区是否活跃到值得投入、未来会不会维护、商业上是否可行。这些需要另外的依据。

---

## 2. 取证方式

| 级别 | 方式 | 说明 |
|---|---|---|
| 一手 | `git clone --depth 1` 后本地读文件、跑统计命令 | 报告中的目录、类名、表名、行数、版本号全部来自这里 |
| 一手 | GitHub REST API `/repos/{owner}/{repo}` | star、fork、license 标识、created_at、pushed_at |
| 二手 | 仓库内 README / docs | 只作为"项目自述"，引用时标明"README 声称" |
| 不采用 | 搜索引擎摘要、第三方文章、AI 记忆 | 一律不写进报告 |

所有克隆固定在具体 commit，报告头部记录 commit hash 与日期。源码保留在 `_sources/`，任何人可用第 6 节的命令复核。

---

## 3. 证据标记

报告中的每一条结论后面按情况带标记：

- **【实证】**：我在本地源码/命令输出中直接看到。附文件路径或命令结果。
- **【自述】**：来自项目 README、官网、代码注释的声明，未被代码验证。必须原样保留"声称"二字。
- **【未核实】**：无法在本地确认，或本次未读取。禁止用推测填补。

示例：

> 运输订单状态有 7 个：【实证】`org/openwms/tms/TransportOrderState.java`
> 支持多租户：【自述】README 列出，本次未在代码中找到租户隔离实现 → 【未核实】

---

## 4. 八条红线（杜绝编撰与推理）

1. **代码里没有的功能，不写成"已有"**。README 说了但代码没找到，只能写"README 声称，代码未核实"。
2. **不推断路线图**。没有 `ROADMAP` 文件就不写"计划支持"。
3. **不把 star 数当质量**。star 只作为元数据记录，不参与任何评价句。
4. **不把 fork 当原项目**。克隆地址与 commit 必须指向报告标题中的仓库。
5. **不猜许可证**。只抄 `LICENSE` / `COPYING` 原文关键句，并注明是原文；许可证兼容性不做法律判断，只提示"需法务确认"。
6. **不根据命名猜实现**。类名叫 `XxxScheduler` 不代表有调度在跑，必须看到被谁调用或配置启用。
7. **不写性能、并发、生产可用性结论**。本次没有压测、没有部署运行，一律标【未核实】。
8. **不把"有这个类/表"写成"有这个功能"**。功能结构必须落到菜单、页面或接口入口；只有实体或表时，只能写"数据模型支持"，不能写"提供了 XX 功能"。这条是本批第一版报告的失效点——初版只写了代码模块，没写功能结构，已在本轮补齐。

## 5. 报告固定结构（每份一致）

```
1. 基本信息        仓库地址、commit、抓取日期、star/fork、主语言、许可证原文结论
2. 它是什么 / 不是什么   原文引用 + 明确的边界（是 WMS？是 OMS？是 WCS？）
3. 技术栈          构建文件中的框架与版本，逐条带文件路径
4. 代码规模        Java/Groovy 文件数、代码行数、Controller 数、SQL 建表数
5. 功能结构与代码模块
   5.1 功能结构    功能树 + 每项的代码入口 + 数据来源类型（见 5.1 说明）
   5.2 代码模块    顶层目录与子模块清单（settings.gradle / pom modules / 目录）
6. 数据模型        表名或实体类清单（关键单据、库存、任务、主数据）
7. 核心机制        状态机、任务模型、算法、插件点等可读到的实现，附类名
8. 接口与集成      对外 API、消息、设备/ERP 对接方式（有则写，无则写"未发现"）
9. 部署方式        docker-compose / Dockerfile / 应用服务器 / 中间件依赖
10. 活跃度         默认分支最后提交时间、pushed_at、开放 issue 数
11. 可参考点       每条必须指向文件/表；同时写"不建议参考的部分"
12. 未核实清单     本次没读到、没法确认的内容，逐条列出
```

### 5.1 功能结构的四类来源（可靠性从高到低）

| 类型 | 含义 | 能证明什么 | 不能证明什么 |
|---|---|---|---|
| A 菜单数据 | 初始化 SQL 里的菜单/按钮记录（如 `u_menu`） | 产品定义的完整功能树，含层级与顺序 | 功能是否真的可用 |
| B 页面目录 | 前端 `views` / `pages` 目录 | 有页面就有入口，页面名即功能名 | 后端是否实现、是否只是一个空页面 |
| C 接口路径 | Controller 的 `@RequestMapping` | 有接口就有能力 | 是否有页面、是否有权限、是否被前端调用 |
| D 实体/表 | 实体类、表名 | 数据模型支持这件事 | 是否做了增删改查、是否有业务流程 |

写功能结构时必须标明用的是哪类来源，**不能把 D 类（实体）当 A 类（菜单）写**。例如"有 `wms_inventory_history` 表"只能得出"记录了库存流水"，不能得出"有库存记录页面"。

功能树的末级必须能指到一个代码入口（Controller 路径 / 页面路径 / 菜单 path / 实体类名），指不到的不写。

## 6. 复核命令

```bash
cd humandesign/调研/系统/_sources
git -C <dir> log -1 --format='%H %ad %s' --date=iso
find <dir> -name '*.java' | wc -l
find <dir> -name '*.java' -print0 | xargs -0 cat | wc -l
grep -rhoiE 'create table (if not exists )?`?[a-zA-Z0-9_]+' --include='*.sql' <dir> | wc -l
```

GitHub 元数据原始 JSON 保留在 `_sources/_facts/api_*.json`，统计输出在 `_sources/_facts/*.txt`。
